# Design a URL Shortener: конспект

## Step 1. Requirements

- Пример: длинный URL → короткий alias (`tinyurl.com/y7keocwj`), переход по alias редиректит на оригинал.
- **100M URLs в день**, URL как можно короче.
- Символы: `0-9`, `a-z`, `A-Z` (62 символа).
- URL **нельзя удалять и обновлять** (для простоты).
- Use cases: **URL shortening**, **URL redirecting**, high availability, scalability, fault tolerance.

## Back-of-the-envelope

- Write: 100M / 24 / 3600 ≈ **1160 writes/sec**
- Read (read:write = 10:1): ≈ **11 600 reads/sec**
- За 10 лет: 100M × 365 × 10 = **365 млрд записей**
- Средний URL ~100 bytes: 365B × 100 B = **365 TB** за 10 лет

## Step 2. High-level design

### API (REST)

- **URL shortening**: `POST api/v1/data/shorten`, параметр `{longUrl}`, возвращает shortURL.
- **URL redirecting**: `GET api/v1/{shortUrl}`, возвращает longURL для HTTP redirect.

### 301 vs 302 redirect (частый вопрос)

- **301 (permanent)**: браузер кэширует ответ, повторные запросы не доходят до shortener. Меньше нагрузки на сервер.
- **302 (temporary)**: каждый запрос идёт через shortener. Лучше для **analytics** (click rate, источник кликов).
- Приоритет нагрузка: 301. Приоритет аналитика: 302.

### Базовая идея

- Redirect: hash table `<shortURL, longURL>`, `longURL = hashTable.get(shortURL)`.
- Shortening: нужна hash function, где каждый longURL даёт один hashValue, и каждый hashValue можно вернуть в longURL.

## Step 3. Deep dive

### Data model

- Hash table в памяти для реального мира не подходит (память дорогая и ограничена). Хранить `<shortURL, longURL>` в **relational DB**: таблица с колонками `id`, `shortURL`, `longURL`.

### Длина hashValue

- Ищем минимальное n, где **62^n ≥ 365 млрд**.
- n = 7: 62^7 ≈ **3.5 трлн**, хватает с запасом. **Длина = 7**.

### Подход 1: hash + collision resolution

- Берём CRC32 / MD5 / SHA-1. Даже самый короткий (CRC32) длиннее 7 символов.
- Берём **первые 7 символов** хеша, но возможны **коллизии**.
- Разрешение коллизий: рекурсивно дописываем предопределённую строку, пока коллизия не исчезнет.
- Минус: **дорого** проверять в DB на каждый запрос. Ускоряет **bloom filter** (space-efficient вероятностная структура для проверки членства в множестве).

### Подход 2: base 62 conversion

- Переводим число (ID) из base 10 в base 62. Маппинг: 0-9 → 0-9, 10-35 → a-z, 36-61 → A-Z.
- Пример: 11157 = 2×62² + 55×62¹ + 59×62⁰ = [2, 55, 59] → **2TX**.

### Сравнение подходов

| | Hash + collision resolution | Base 62 conversion |
|---|---|---|
| Длина | фиксированная (7) | зависит от ID |
| Нужен unique ID generator | нет | **да** |
| Коллизии | есть, нужно разрешать (проверка в DB) | **нет**, ID уникален |
| Предсказуемость следующего URL | нет, нельзя угадать | можно угадать, если ID растёт на 1 (security concern) |

Таблица составлена мной, в тексте главы (Table 8-3) её нет, поэтому часть пунктов моя интерпретация.

В книге выбран **base 62**.

### URL shortening flow

1. Вход: longURL.
2. Проверяем, есть ли longURL в DB.
3. Есть: возвращаем существующий shortURL.
4. Нет: **unique ID generator** (Chapter 7) выдаёт новый ID (primary key).
5. Конвертируем ID в shortURL через **base 62**.
6. Сохраняем в DB строку: `id`, `shortURL`, `longURL`.

Пример: ID `2009215674938` → `zn9edcu`.

### URL redirecting flow

Читаний больше, чем записей, поэтому mapping лежит в **cache**.

1. Пользователь открывает short URL.
2. **Load balancer** → web servers.
3. shortURL в cache: сразу возвращаем longURL.
4. Нет в cache: берём из DB. Нет и там: скорее всего **невалидный** shortURL.
5. longURL возвращается пользователю.

## Step 4. Wrap up: что добавить

- **Rate limiter**: защита от массовых запросов на shortening (по IP и другим правилам), Chapter 4.
- **Web server scaling**: web tier stateless, легко добавлять и убирать серверы.
- **Database scaling**: replication и sharding.
- **Analytics**: сколько кликов, когда кликают.
- **Availability, consistency, reliability**: ядро любой большой системы (Chapter 1).

## Шпаргалка на интервью

1. Уточни: объём (100M/день), длина, символы, удаление/обновление.
2. Оценка: **1160 write/s, 11 600 read/s, 365B записей, 365 TB**.
3. API: `POST /shorten`, `GET /{shortUrl}`.
4. Объясни **301 vs 302** (нагрузка vs analytics).
5. Длина **7** символов (62^7 ≈ 3.5 трлн ≥ 365B).
6. Два подхода: **hash + collision resolution** (bloom filter) и **base 62** (нужен unique ID generator, ID из Chapter 7).
7. Shortening flow: проверка в DB, генерация ID, base 62, запись.
8. Redirect flow: **cache → DB**, load balancer.
9. Wrap up: rate limiter, scaling (stateless web, replication/sharding), analytics.
