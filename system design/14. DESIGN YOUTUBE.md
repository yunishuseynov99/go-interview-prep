# Design YouTube: конспект

## Step 1. Requirements

- Фичи: **upload video** и **watch video**
- Клиенты: mobile apps, web, smart TV
- **5M DAU**, в среднем 30 минут в день
- Международные пользователи
- Принимаем большинство форматов и разрешений
- **Encryption** нужен
- Макс. размер видео **1 GB** (small/medium)
- Использовать существующие **cloud services** (строить всё с нуля нереально)

**Целевые свойства:** быстрая загрузка, smooth streaming, смена качества, низкая стоимость инфраструктуры, high availability/scalability/reliability.

## Back-of-the-envelope

- 5M DAU, 5 видео в день, 10% юзеров заливают 1 видео в день, средний размер **300 MB**
- Storage: 5M × 10% × 300 MB = **150 TB в день**
- CDN (CloudFront, ~$0.02 за GB): 5M × 5 × 0.3 GB × $0.02 = **$150 000 в день**
- Вывод: **CDN очень дорогой**, это главный объект оптимизации стоимости.

## Step 2. High-level design

Почему используем готовые сервисы: на интервью важно выбрать правильную технологию, а не объяснять её внутренности. Даже Netflix использует AWS, а Facebook использует Akamai CDN.

**Три компонента:** **Client**, **CDN** (отсюда стримится видео), **API servers** (всё остальное: feed, upload URL, metadata, signup).

### Video uploading flow

**Компоненты:**
- **Load balancer**, **API servers**
- **Metadata DB** (sharded + replicated) и **Metadata cache**
- **Original storage** (**blob storage**) для исходных видео
- **Transcoding servers**: конвертируют формат (MPEG, HLS и т.д.) под разные устройства и bandwidth
- **Transcoded storage** (blob)
- **CDN**
- **Completion queue** (message queue с событиями завершения транскодинга)
- **Completion handler** (workers, обновляют metadata DB и cache)

Два параллельных процесса:

**a. Загрузка самого видео:**
1. Видео в original storage
2. Transcoding servers забирают и транскодят
3. После завершения параллельно: (3a) transcoded video → transcoded storage → CDN; (3b) событие в completion queue → completion handler обновляет metadata DB и cache
4. API servers сообщают клиенту, что видео готово

**b. Обновление metadata:** пока файл грузится, клиент параллельно шлёт metadata (имя, размер, формат), API servers обновляют cache и DB.

### Video streaming flow

- **Streaming** (поток, ничего не качаем целиком) vs **download** (копируем весь файл).
- **Streaming protocols**: MPEG-DASH, Apple HLS, Microsoft Smooth Streaming, Adobe HDS. Разные протоколы поддерживают разные кодировки и плееры, нужно выбрать под свои use cases. Названия помнить не обязательно.
- Видео стримится **напрямую с CDN**, с ближайшего edge server, поэтому latency минимальная.

## Step 3. Deep dive

### Video transcoding

**Зачем нужен:**
- Raw video занимает огромный объём (час HD 60fps это сотни GB)
- Устройства и браузеры поддерживают разные форматы
- Высокое разрешение для быстрого интернета, низкое для медленного
- Сеть меняется (особенно на mobile), нужна **адаптивная смена качества**

**Формат состоит из двух частей:**
- **Container**: корзина для video, audio, metadata (.avi, .mov, .mp4)
- **Codec**: алгоритм сжатия и распаковки (H.264, VP9, HEVC)
- **Bitrate**: скорость обработки битов, выше значит лучше качество, но нужна мощность и быстрый интернет

### DAG model

- Транскодинг дорогой, а требования у авторов разные (watermark, свой thumbnail, HD или нет).
- Решение: **DAG (directed acyclic graph)**, задачи описываются стадиями, выполняются последовательно или параллельно (подход Facebook).
- Видео разделяется на video, audio, metadata. Задачи: **inspection** (проверка качества и целостности), **video encodings** (разрешения, codec, bitrate), **thumbnail** (загружен или автогенерация), **watermark**.

### Transcoding architecture (6 компонентов)

**1. Preprocessor**
- **Video splitting** на **GOP** (Group of Pictures): независимо проигрываемый кусок из нескольких секунд. Для старых клиентов, не умеющих делить видео, это делает preprocessor.
- **DAG generation** из конфигурационных файлов.
- **Cache data**: хранит GOPs и metadata в temporary storage, при ошибке encoding можно ретраить.

**2. DAG scheduler**: разбивает граф на **stages** и кладёт задачи в task queue. Пример: stage 1 это video/audio/metadata, stage 2 это video encoding, thumbnail, audio encoding.

**3. Resource manager**
- **Task queue** (priority queue задач)
- **Worker queue** (priority queue с загрузкой воркеров)
- **Running queue** (текущие пары task/worker)
- **Task scheduler**: берёт задачу с высшим приоритетом, выбирает оптимального воркера, запускает, пишет пару в running queue, по завершении удаляет.

**4. Task workers**: выполняют задачи из DAG, разные воркеры под разные задачи.

**5. Temporary storage**: metadata в memory (часто читается, маленькая), видео и аудио в blob storage. Очищается после завершения обработки.

**6. Encoded video**: финальный результат, например `funny_720p.mp4`.

### System optimizations

**Speed**
- **Parallel upload**: делим видео на **GOP-chunks** на клиенте, получаем быстрые **resumable uploads** при сбое.
- **Upload centers рядом с пользователем**: CDN как upload centers (США в Северную Америку, Китай в Азию).
- **Parallelism everywhere**: между модулями (download → encoding → upload) стоят **message queues**. Encoding не ждёт download, обрабатывает события параллельно. Система становится loosely coupled.

**Safety**
- **Pre-signed upload URL**: клиент просит у API servers URL с правами на конкретный объект, затем грузит видео по нему. Только авторизованные пользователи и нужное место. В Azure это называется **Shared Access Signature**.
- **Защита видео от кражи:**
  - **DRM**: Apple FairPlay, Google Widevine, Microsoft PlayReady
  - **AES encryption** с authorization policy
  - **Visual watermarking**

**Cost saving** (YouTube следует **long-tail distribution**: немного популярных видео и много почти непросматриваемых):
1. **Только популярные видео из CDN**, остальные с собственных high capacity storage серверов.
2. Для непопулярных **не хранить много версий encoding**, короткие видео кодировать **on-demand**.
3. Видео, популярные в одном регионе, **не раскидывать по другим**.
4. **Собственный CDN** и партнёрство с **ISP** (как Netflix): имеет смысл только для крупных компаний, снижает bandwidth costs.
- Перед оптимизацией анализируем **историю просмотров**.

### Error handling

**Два типа ошибок:**
- **Recoverable** (например, segment не транскодился): retry несколько раз, если не помогает, вернуть error code клиенту.
- **Non-recoverable** (например, malformed video): остановить задачи по этому видео, вернуть error code.

**Playbook по компонентам:**

| Компонент | Что делаем |
|---|---|
| Upload error | retry |
| Split video error | клиент не умеет GOP: всё видео на сервер, split на server-side |
| Transcoding error | retry |
| Preprocessor error | перегенерировать DAG |
| DAG scheduler error | перепланировать задачу |
| Resource manager queue down | использовать replica |
| Task worker down | retry на новом воркере |
| API server down | stateless, запрос уйдёт на другой |
| Metadata cache down | данные реплицированы, поднять новый сервер |
| Metadata DB master down | promote одного из slave в master |
| Metadata DB slave down | читаем с другого slave, поднимаем замену |

## Step 4. Wrap up

- **Scale API tier**: stateless, горизонтальное масштабирование.
- **Scale database**: replication и sharding.
- **Live streaming**: схожие этапы (upload, encode, stream), отличия:
  - выше требования к **latency**, возможно другой streaming protocol;
  - меньше нужды в **parallelism** (чанки обрабатываются в реальном времени);
  - другой **error handling**, ничего долгого недопустимо.
- **Video takedowns**: удаление видео с нарушением copyright, порнографии и т.п. Часть находится при upload, часть через user flagging.

## Шпаргалка на интервью

1. Уточни: фичи (upload + watch), клиенты, 5M DAU, 1 GB лимит, **использовать cloud (CDN + blob storage)**.
2. Оценка: **150 TB/день storage, $150K/день CDN**.
3. Три компонента: client, CDN, API servers.
4. Upload flow: original storage → **transcoding** → transcoded storage → CDN, плюс **completion queue/handler** и параллельный update metadata.
5. Streaming: протоколы (**DASH, HLS**), раздача с ближайшего **CDN edge**.
6. Transcoding: **container + codec + bitrate**, **DAG**, preprocessor / DAG scheduler / resource manager / task workers.
7. Speed: **GOP chunks + resumable upload**, upload centers, **message queues** для parallelism.
8. Safety: **pre-signed URL**, **DRM / AES / watermark**.
9. Cost: **long-tail**, популярное из CDN, остальное со своих серверов, on-demand encoding, свой CDN с ISP.
10. Errors: **recoverable (retry) vs non-recoverable**, playbook по компонентам.
11. Wrap up: scaling, live streaming, takedowns.
