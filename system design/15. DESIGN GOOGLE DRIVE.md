# Design Google Drive: конспект

## Step 1. Requirements

- Фичи: **upload/download**, **file sync** между устройствами, **notifications**, file revisions, sharing
- Клиенты: web и mobile
- Любой тип файла, макс. **10 GB**
- Файлы в storage **encrypted**
- **10M DAU**
- Вне scope: совместное редактирование Google Docs

**Нефункциональные:**
- **Reliability**: потеря данных недопустима
- **Fast sync speed**
- **Bandwidth usage**: не гонять лишний трафик (особенно на mobile)
- **Scalability**, **high availability**

## Back-of-the-envelope

- 50M зарегистрированных, 10M DAU, 10 GB бесплатно на юзера
- 2 upload в день, файл в среднем 500 KB, read:write = 1:1
- Выделено места: 50M × 10 GB = **500 PB**
- Upload QPS = 10M × 2 / 24 / 3600 ≈ **240**
- Peak QPS = 2 × QPS = **480**

## Step 2. High-level design

### Эволюция: от single server к распределённой системе

**Single server:** web server (Apache), DB (MySQL) для metadata, директория `drive/` для файлов. Внутри **namespaces** (по одному на пользователя). Файл идентифицируется как namespace + relative path.

**APIs** (все с auth и HTTPS/SSL):
1. **Upload**: simple upload (маленькие файлы) и **resumable upload** (большие файлы, риск обрыва). Resumable в 3 шага: запрос resumable URL → загрузка с мониторингом состояния → resume при обрыве.
2. **Download**: параметр `path`.
3. **Get file revisions**: параметры `path` и `limit`.

**Закончилось место:**
- Сначала **sharding** хранилища по `user_id`.
- Затем переход на **Amazon S3** (object storage), поддерживает **same-region** и **cross-region replication**. Bucket это как папка. Файлы в нескольких регионах защищают от потери данных.

**Улучшения:**
- **Load balancer**
- Больше **web servers** (легко добавлять и убирать)
- **Metadata DB** вынесена с сервера (против SPOF), с replication и sharding
- **File storage** в S3, репликация в двух регионах

### Sync conflicts

- Конфликт: два пользователя меняют один файл одновременно.
- Стратегия: **первая обработанная версия выигрывает**, вторая получает конфликт.
- Пользователю показываются обе копии: локальная и последняя серверная. Он может **merge** или **override**.

### Компоненты high-level design

- **Block servers**: режут файл на **blocks**, у каждого уникальный hash (хранится в metadata DB), блоки грузятся в S3. Для сборки файла блоки соединяются в нужном порядке. Размер блока: до **4 MB** (по Dropbox).
- **Cloud storage** (S3)
- **Cold storage**: для неактивных данных
- **Load balancer**
- **API servers**: всё, кроме upload (auth, профиль, metadata)
- **Metadata DB**: users, files, blocks, versions. Сами файлы в облаке.
- **Metadata cache**
- **Notification service**: **pub/sub**, уведомляет клиентов, что файл добавлен/изменён/удалён, чтобы они забрали изменения.
- **Offline backup queue**: хранит изменения для офлайн-клиентов, синк при возвращении онлайн.

## Step 3. Deep dive

### Block servers: экономия трафика

Две оптимизации:
- **Delta sync**: при изменении файла синхронизируются только **изменённые blocks**.
- **Compression**: по типу файла (gzip, bzip2 для текста, другие алгоритмы для изображений и видео).

Block server: **split → compress → encrypt → upload в cloud storage**. Пример delta sync: изменились block 2 и block 5, грузятся только они.

### Strong consistency

- Система требует **strong consistency** по умолчанию: клиенты не должны видеть файл по-разному.
- Memory cache по умолчанию **eventually consistent**. Для strong consistency:
  - данные в cache replicas и master совпадают;
  - **invalidate cache** при записи в DB.
- Выбрана **relational DB**, потому что **ACID** из коробки. В NoSQL ACID пришлось бы реализовывать вручную в sync logic.

### Metadata DB schema

- **User**: username, email, фото
- **Device**: device info, `push_id` для mobile push, у юзера может быть несколько
- **Namespace**: корневая директория юзера
- **File**: последняя версия файла
- **File_version**: история версий, строки **read-only** (целостность истории)
- **Block**: блоки файла, любую версию можно собрать из блоков в нужном порядке

### Upload flow (два параллельных запроса от client 1)

**Add file metadata:**
1. Client 1 шлёт metadata нового файла
2. Metadata сохраняется в DB, статус **"pending"**
3. Уведомляется notification service
4. Тот уведомляет client 2, что файл загружается

**Upload файла:**
1. Client 1 грузит содержимое на **block servers**
2. Block servers режут на blocks, сжимают, шифруют, шлют в cloud storage
3. Cloud storage вызывает **upload completion callback** на API servers
4. Статус в metadata DB меняется на **"uploaded"**
5. Notification service получает событие
6. Уведомляет client 2, что файл полностью загружен

### Download flow

Клиент узнаёт об изменении двумя способами:
- **Онлайн**: notification service сообщает, что нужно забрать изменения.
- **Офлайн**: изменения сохраняются, при возвращении онлайн клиент их подтягивает.

Дальше: клиент запрашивает **metadata** через API servers → получает → запрашивает у block servers → block servers берут blocks из cloud storage → клиент собирает файл из блоков.

### Notification service: long polling vs WebSocket

- **Long polling** (его использует Dropbox) или **WebSocket** (persistent bi-directional).
- Выбран **long polling**:
  1. Коммуникация **не bi-directional**: сервер шлёт клиенту, обратно нет.
  2. WebSocket подходит для real-time bi-directional (чаты). В Drive уведомления **редкие, без bursts**.
- Как работает: клиент держит long poll соединение, при изменении файла соединение закрывается, клиент идёт в metadata server за изменениями. После ответа или timeout сразу открывает новое соединение.

### Экономия storage

Версии хранятся в нескольких data centers, место заканчивается быстро. Три техники:
1. **De-duplicate data blocks** на уровне аккаунта: блоки с одинаковым hash идентичны.
2. **Intelligent backup strategy**:
   - **лимит числа версий**, старейшая заменяется новой;
   - хранить **только ценные версии** (больше вес у свежих), число версий определяется экспериментально.
3. **Cold storage** для неактивных (месяцы/годы) данных, например **S3 Glacier**: намного дешевле S3.

### Failure handling

| Компонент | Что происходит |
|---|---|
| **Load balancer** | Secondary становится активным, балансеры мониторят друг друга через **heartbeat** |
| **Block server** | Другие серверы подхватывают незавершённые задачи |
| **Cloud storage** | S3 реплицирован по регионам, берём из другого региона |
| **API server** | Stateless, трафик перенаправляется load balancer'ом |
| **Metadata cache** | Реплицирован, поднимаем новый сервер взамен упавшего |
| **Metadata DB: master down** | Promote одного slave в master, поднимаем новый slave |
| **Metadata DB: slave down** | Читаем с другого slave, поднимаем замену |
| **Notification service** | Все long poll соединения теряются, клиенты переподключаются к другому серверу (у Dropbox 1M+ соединений на машину). **Переподключение медленное**, всех сразу не переподключить |
| **Offline backup queue** | Очереди реплицированы, consumers пере-подписываются на backup queue |

## Step 4. Wrap up

**Что подчеркнуть:** сочетание **strong consistency**, низкого bandwidth и быстрого sync. Два потока: **file metadata** и **file sync**. Notification service на **long polling**.

**Альтернатива: upload напрямую в cloud storage с клиента** (минуя block servers).
- Плюс: быстрее, файл передаётся один раз.
- Минусы:
  1. Логику chunking, compression, encryption придётся реализовывать на **каждой платформе** (iOS, Android, Web): ошибки и большие трудозатраты. У нас всё в одном месте: block servers.
  2. Клиент легко взломать, **encryption на клиенте не идеальна**.

**Эволюция:** вынести online/offline логику в отдельный **presence service**, чтобы её могли использовать другие сервисы.

## Шпаргалка на интервью

1. Уточни: upload/download, sync, notifications, 10 GB лимит, encryption, 10M DAU.
2. Оценка: **500 PB выделено, 240 QPS, peak 480**.
3. Эволюция: single server → sharding → **S3 с cross-region replication** → load balancer, stateless web servers, вынесенная metadata DB.
4. **Sync conflicts**: первый выигрывает, второму показываем обе копии (merge или override).
5. **Block servers**: split → compress → encrypt → upload, **delta sync** + compression, блок до 4 MB.
6. **Strong consistency**: relational DB (ACID) + invalidate cache при записи.
7. Schema: user, device, namespace, file, **file_version (read-only)**, block.
8. Upload flow: параллельно **metadata (pending → uploaded)** и **blocks**, callback от storage, уведомление через notification service.
9. Download flow: notification → metadata → blocks → сборка файла. Офлайн: **offline backup queue**.
10. Notification: **long polling**, потому что односторонне и редко.
11. Storage saving: **dedup блоков по hash**, лимит версий, **cold storage (Glacier)**.
12. Failures: у каждого компонента своя стратегия (replica, failover, stateless).
13. Wrap up: upload напрямую с клиента (плюсы и минусы), presence service.
