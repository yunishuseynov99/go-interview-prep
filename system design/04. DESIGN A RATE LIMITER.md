# Design a Rate Limiter: конспект

## Что это и зачем

**Rate limiter** ограничивает число запросов клиента за период. Лишние запросы блокируются. Примеры: не больше 2 постов в секунду, 10 аккаунтов в день с одного IP.

**Зачем нужен:**
- Защита от **DoS** (намеренного и случайного), предотвращает resource starvation.
- **Reduce cost**: меньше серверов, особенно если платишь за вызовы сторонних API.
- Защита серверов от перегрузки (боты, misbehavior).

## Step 1. Requirements

Уточнили у интервьюера: **server-side API rate limiter**, гибкие правила (IP, user ID и т.д.), большой scale, **distributed** окружение, отдельный сервис или в коде на твой выбор, юзеров надо информировать о throttling.

Итоговые требования:
- Точное ограничение лишних запросов.
- **Low latency**: не тормозит HTTP response.
- Минимум памяти.
- Distributed rate limiting (общий для нескольких серверов).
- Понятные exceptions для юзера.
- **High fault tolerance**: если rate limiter (например, cache) упал, система продолжает работать.

## Step 2. High-level design

### Где разместить

- **Client-side**: ненадёжно, запросы легко подделать, нет контроля над клиентом.
- **Server-side**: в коде API.
- **Middleware / API gateway**: throttling перед API servers. Превышение возвращает **HTTP 429 (Too Many Requests)**.
- **API gateway** это managed service: rate limiting, SSL termination, authentication, IP whitelisting, static content.

**Что выбрать (зависит от контекста):**
- Оцени tech stack (язык, cache).
- Нужен полный контроль над алгоритмом: server-side. Third-party gateway ограничивает выбор.
- Уже есть microservices и API gateway: добавляй rate limiter туда.
- Мало ресурсов на разработку: бери commercial API gateway.

### Алгоритмы (главная часть для интервью)

**1. Token bucket**
- Bucket с фиксированной capacity, токены добавляются с постоянной скоростью (refill). Запрос забирает 1 токен. Нет токенов: запрос drop.
- Параметры: **bucket size**, **refill rate**.
- Сколько buckets: отдельный на каждый API endpoint, на каждый IP, или один global bucket.
- Плюсы: простой, memory efficient, **допускает burst**. Минус: сложно подобрать параметры.
- Используют: Amazon, Stripe.

**2. Leaking bucket**
- Как token bucket, но запросы обрабатываются с **фиксированной скоростью**. Реализация: **FIFO queue**. Очередь полная: запрос drop.
- Параметры: **bucket (queue) size**, **outflow rate**.
- Плюсы: memory efficient, стабильный outflow. Минусы: burst забивает очередь старыми запросами, новые режутся; два параметра сложно тюнить.
- Используют: Shopify.

**3. Fixed window counter**
- Timeline делится на окна фиксированного размера, у каждого счётчик. Дошёл до threshold: запросы drop до следующего окна.
- Плюсы: простой, memory efficient.
- Минус: **burst на границе окон** пропускает до 2× от квоты. Пример: лимит 5/мин, 5 запросов в конце одной минуты и 5 в начале следующей: за окно 2:00:30-2:01:30 прошло 10.

**4. Sliding window log**
- Хранит **timestamps** запросов (Redis sorted sets). На новом запросе: удалить устаревшие timestamps, добавить новый, если размер лога ≤ лимита, то accept, иначе reject.
- Плюс: **очень точный** в любом rolling window.
- Минус: **много памяти**, timestamp хранится даже у rejected запросов.

**5. Sliding window counter** (гибрид fixed counter + sliding log)
- Формула: `requests в текущем окне + requests в предыдущем окне × overlap % rolling window с предыдущим окном`.
- Пример: лимит 7/мин, 5 в прошлой минуте, 3 в текущей, запрос на 30% текущей минуты: 3 + 5 × 0.7 = 6.5, округляем до 6, пропускаем.
- Плюсы: сглаживает spikes, memory efficient.
- Минус: **приближение**, предполагает равномерное распределение в предыдущем окне. По данным Cloudflare, ошибка около 0.003% на 400M запросов.

### Сравнение (для быстрого ответа)

| Алгоритм | Burst | Память | Точность |
|---|---|---|---|
| Token bucket | допускает | низкая | средняя |
| Leaking bucket | сглаживает (fixed rate) | низкая | средняя |
| Fixed window | проблема на границах | низкая | низкая |
| Sliding window log | нет | **высокая** | **высокая** |
| Sliding window counter | сглаживает | низкая | высокая (approx) |

Таблица составлена мной по описанию алгоритмов, в книге её нет.

### Базовая архитектура

- Нужен **counter** на user/IP/etc. Превысил лимит: запрос запрещён.
- Хранить в DB плохо (медленный disk). Берём **in-memory cache**, например **Redis**, с командами:
  - **INCR**: увеличить счётчик на 1.
  - **EXPIRE**: timeout, по истечении счётчик удаляется.
- Flow: клиент, затем middleware, middleware берёт counter из Redis. Лимит достигнут: reject. Нет: пропускаем на API servers и делаем INCR.

## Step 3. Deep dive

### Rules

- Правила пишутся в **config files** на диске (пример Lyft: domain, descriptors, `rate_limit` с unit и `requests_per_unit`). Пример: 5 marketing messages в день, 5 логинов в минуту.

### Что делать с превышением

- Возвращаем **429**. Иногда запрос кладут в **queue** на обработку позже (пример: заказы при перегрузке).

### Headers

- `X-Ratelimit-Remaining`: сколько запросов осталось в окне.
- `X-Ratelimit-Limit`: сколько вызовов можно за окно.
- `X-Ratelimit-Retry-After`: через сколько секунд можно повторить.
- При 429 возвращается Retry-After.

### Detailed design

- Правила на диске, **workers** периодически подтягивают их в cache.
- Запрос идёт в middleware, он берёт правила из cache, а counter и last request timestamp из Redis.
- Не limited: forward на API servers. Limited: 429, а сам запрос drop или в queue.

### Distributed environment (частый вопрос)

**Race condition**
- Схема read counter → check → increment не атомарна. Два запроса одновременно читают 3, оба пишут 4, а должно быть 5.
- Locks решают, но **сильно замедляют**.
- Решения: **Lua script** (атомарно в Redis) и **sorted sets** в Redis.

**Synchronization issue**
- Несколько rate limiter серверов: клиент может попасть на любой, а у каждого своя картина.
- **Sticky sessions**: плохо, не scalable и не flexible.
- Правильно: **centralized data store** (Redis), общий для всех rate limiter'ов.

### Performance optimization

- **Multi-data center / edge servers**: трафик идёт на ближайший edge, меньше latency (у Cloudflare 194 edge locations по состоянию на 2020).
- Синхронизация данных с **eventual consistency**.

### Monitoring

Проверяем, что эффективны **алгоритм** и **правила**:
- Правила слишком строгие: режутся валидные запросы, ослабляем.
- Неэффективен при внезапных всплесках (flash sales): меняем алгоритм на поддерживающий burst, например **token bucket**.

## Step 4. Wrap up: что добавить в конце

- **Hard vs soft** rate limiting: hard никогда не превышает threshold, soft допускает превышение на короткое время.
- Rate limiting на разных уровнях OSI: в главе рассмотрен L7 (HTTP), но можно, например, по IP через **Iptables** (L3).
- Как клиенту **избегать** лимитов:
  - client cache, чтобы не делать частые вызовы;
  - знать лимиты и не слать пачки запросов;
  - ловить exceptions и корректно восстанавливаться;
  - **back off** в retry logic.

## Шпаргалка на интервью

1. Уточни: client или server-side, по каким ключам (IP, user ID), scale, distributed ли, отдельный сервис или код.
2. Предложи размещение: **middleware / API gateway**, ответ **429**.
3. Назови алгоритмы и выбери, обосновав. Дефолт: **token bucket** (burst, просто, memory efficient).
4. Хранилище: **Redis** (INCR + EXPIRE), не DB.
5. Правила в config, workers грузят их в cache.
6. Distributed: **race condition** (Lua / sorted sets) и **sync** (centralized Redis).
7. Fault tolerance: падение Redis не должно ронять систему.
8. Monitoring, hard vs soft, rate limiting на других уровнях, client best practices.
