# Design a Search Autocomplete System: конспект

## Что это

**Autocomplete** (typeahead, search-as-you-type): пока юзер печатает, показываем подходящие запросы. Задача также известна как **"design top k"** (top k most searched queries).

## Step 1. Requirements

- Совпадение только **с начала** запроса (prefix)
- Возвращаем **5** подсказок
- Ранжирование по **popularity** (историческая частота запросов)
- Без spell check и autocorrect
- Английский, только lowercase буквы (multi-language обсуждаем в конце)
- **10M DAU**

**Нефункциональные:**
- **Fast response**: до **100 ms**, иначе stuttering (по статье про Facebook)
- **Relevant** и **sorted** по популярности
- **Scalable**
- **Highly available**

## Back-of-the-envelope

- 10M DAU × 10 searches/день, запрос ~20 bytes (4 слова × 5 символов, ASCII)
- На каждый введённый символ уходит запрос, в среднем 20 запросов на поиск
- **QPS** = 10M × 10 × 20 / 24 / 3600 ≈ **24 000**
- **Peak QPS** = 2 × QPS ≈ **48 000**
- 20% запросов новые: 10M × 10 × 20 B × 20% = **0.4 GB новых данных в день**

## Step 2. High-level design

Два сервиса:
- **Data gathering service**: собирает запросы и агрегирует (в начале условно real-time).
- **Query service**: по prefix возвращает **top 5** самых частых запросов.

Базовый вариант: **frequency table** (`query`, `frequency`) в DB и SQL с `LIKE 'prefix%'`, `ORDER BY frequency DESC LIMIT 5`. Подходит для малых данных, на больших DB становится **bottleneck**.

## Step 3. Deep dive

### Trie (prefix tree)

- Tree-like структура для хранения строк (от "retrieval"). Корень это пустая строка. Каждый node хранит символ и имеет до 26 children. Каждый node это слово или prefix.
- Для сортировки по частоте во node добавляется **frequency**.

**Базовый алгоритм top k** (p = длина prefix, c = число children, n = число nodes):
1. Найти prefix: **O(p)**
2. Обойти subtree и собрать валидные запросы: **O(c)**
3. Отсортировать и взять top k: **O(c log c)**

Итого O(p) + O(c) + O(c log c). В худшем случае обходим почти весь trie, это **медленно**.

**Две оптимизации:**
1. **Ограничить max длину prefix** (например, 50): поиск prefix становится **O(1)**.
2. **Кэшировать top k запросов в каждом node**: возврат top k становится **O(1)**. Цена: много памяти. **Trading space for time** оправдан, так как latency критична.

После оптимизаций выборка top k за **O(1)**.

### Data gathering service (redesign)

Real-time обновление trie **непрактично**:
- Миллиарды запросов в день, обновление trie на каждый замедлит query service.
- Топ подсказок со временем меняется слабо, часто обновлять не нужно.

Компоненты:
- **Analytics Logs**: сырые данные запросов, **append-only**, без индексов.
- **Aggregators**: агрегируют логи в нужный формат. Для real-time (Twitter) окно короткое, для большинства случаев хватает **раз в неделю**. В интервью уточни, важен ли real-time. Принимаем, что trie пересобирается **еженедельно**.
- **Aggregated Data**: например, (query, start time of week, frequency).
- **Workers**: асинхронные задачи по расписанию, строят trie и пишут в Trie DB.
- **Trie Cache**: **distributed cache**, держит trie в памяти, еженедельный snapshot из DB.
- **Trie DB**: persistent storage. Два варианта:
  1. **Document store** (MongoDB): периодически сериализуем snapshot trie.
  2. **Key-value store**: каждый **prefix = key**, данные node = **value**.

### Query service (redesign)

Flow:
1. Запрос → **load balancer**.
2. LB → API servers.
3. API servers берут данные из **Trie Cache** и формируют подсказки.
4. При **cache miss** (cache server без памяти или offline) данные подтягиваются в cache, следующие запросы по этому prefix идут из cache.

**Оптимизации скорости:**
- **AJAX requests**: страница не перезагружается.
- **Browser caching**: подсказки в browser cache (Google кэширует на **1 час**: `cache-control: private, max-age=3600`).
- **Data sampling**: логируем 1 из N запросов, чтобы снизить нагрузку на processing и storage.

### Trie operations

- **Create**: workers из aggregated data (Analytics Log/DB).
- **Update**, два варианта:
  1. **Еженедельная пересборка**: новый trie заменяет старый.
  2. **Обновление отдельного node**: медленно, но подходит для маленького trie. Нужно обновить **всех предков до корня**, так как они хранят top queries потомков.
- **Delete**: надо убирать hateful, violent, sexually explicit, dangerous подсказки. Ставим **filter layer перед Trie Cache** (гибко меняются правила). Из DB неподходящие записи удаляются **асинхронно**, чтобы следующий trie строился на чистых данных.

### Scale the storage (sharding)

- Наивный вариант: **shard по первому символу** (a-m на одном сервере, n-z на другом, до 26 серверов). Дальше шардим по второму и третьему символу.
- Проблема: **неравномерное распределение** (слов на "c" намного больше, чем на "x").
- Решение: анализ **исторического распределения** и **shard map manager** (lookup DB, где лежат строки). Пример: один shard для "s" и один для "u"-"z", если объёмы похожи.

## Step 4. Wrap up: follow-up вопросы

- **Multi-language**: хранить **Unicode** символы в nodes trie.
- **Разные топы в разных странах**: отдельные tries по странам, хранить в **CDN** для быстрого отклика.
- **Trending (real-time) queries**: weekly-пересборка не подходит (workers не успевают, строить trie долго). Идеи:
  - уменьшить рабочий набор данных через **sharding**;
  - поменять **ranking model**, дать больший вес **свежим** запросам;
  - **stream processing**: Hadoop MapReduce, Spark Streaming, Storm, Kafka.

## Шпаргалка на интервью

1. Уточни: prefix-only, 5 подсказок, ranking по частоте, язык, DAU (10M).
2. Оценка: **24K QPS, peak 48K, 0.4 GB/день**.
3. Два сервиса: **data gathering** и **query**.
4. Структура: **trie** + **top k в каждом node** + **лимит длины prefix** → O(1).
5. Объясни, почему не real-time обновление: пересборка раз в неделю воркерами.
6. Пайплайн: **logs → aggregators → workers → Trie DB → Trie Cache**.
7. Query: LB → API → Trie Cache; AJAX, browser cache, sampling.
8. Update (weekly rebuild vs update node), delete (**filter layer**).
9. Sharding по префиксу с **shard map manager**.
10. Wrap up: Unicode, tries по странам (CDN), trending через stream processing.
