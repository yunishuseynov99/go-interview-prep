# Design a Notification System: конспект

## Что это

Notification не равно только mobile push. Три формата: **mobile push**, **SMS**, **Email**.

## Step 1. Requirements

- Типы: push, SMS, email
- **Soft real-time**: доставить как можно быстрее, но при высокой нагрузке небольшая задержка допустима
- Устройства: iOS, Android, laptop/desktop
- Триггеры: клиентские приложения, а также **scheduled** на сервере
- Пользователь может сделать **opt-out**
- Объём в день: **10M push, 1M SMS, 5M email**

## Step 2. High-level design

### Как работает каждый тип

**iOS push** (три компонента):
- **Provider**: строит запрос и шлёт в APNS. Данные: **device token** (уникальный идентификатор) и **payload** (JSON).
- **APNS** (Apple Push Notification Service): доставляет на устройство.
- **iOS device**: получатель.

**Android push**: тот же flow, но через **FCM** (Firebase Cloud Messaging).

**SMS**: сторонние сервисы (Twilio, Nexmo), в основном коммерческие.

**Email**: чаще коммерческие сервисы (Sendgrid, Mailchimp), лучше delivery rate и analytics.

### Contact info gathering flow

- При установке приложения или регистрации API servers собирают контакты и пишут в DB.
- Таблицы: **user** (email, phone) и **device** (device tokens). У юзера может быть **несколько устройств**, push уходит на все.

### Initial design

- **Service 1..N** (микросервис, cron job, distributed system) триггерит отправку. Пример: billing шлёт напоминание об оплате.
- **Notification server** (один) даёт API и строит payload.
- **Third-party services** доставляют. Важна **extensibility**: сервис легко подключать и отключать. Пример: FCM недоступен в Китае, там используют Jpush, PushY.

**Три проблемы:**
1. **SPOF**: один сервер.
2. **Hard to scale**: DB, cache и компоненты обработки не масштабируются независимо.
3. **Performance bottleneck**: сборка HTML и ожидание ответов от third-party съедают ресурсы, перегрузка в пике.

### Improved design

Что поменяли:
- **DB и cache** вынесены из notification server.
- Больше notification servers + **automatic horizontal scaling**.
- **Message queues** для decoupling.

**Notification servers:**
- API для сервисов, доступно только **внутри или проверенным клиентам** (защита от спама).
- Базовая **validation** (email, телефон).
- Берут данные для рендера из DB или cache.
- Кладут события в **message queues** для параллельной обработки.

**Cache**: user info, device info, notification templates.
**DB**: users, notifications, settings.
**Message queues**: убирают зависимости, работают как **buffer** при пиках. **Отдельная очередь на каждый тип** уведомления, поэтому падение одного third-party не влияет на остальные.
**Workers**: забирают события из очередей и шлют в third-party.

**Flow:**
1. Сервис вызывает API notification server.
2. Server берёт metadata (user info, device token, settings) из cache/DB.
3. Событие уходит в нужную очередь (например, iOS PN queue).
4. Workers забирают события.
5. Workers отправляют в third-party.
6. Third-party доставляют на устройства.

## Step 3. Deep dive

### Reliability (частые вопросы)

**Как не потерять данные?**
- Уведомления можно **задержать или переупорядочить, но нельзя потерять**.
- Решение: **notification log DB** для персистентности + **retry mechanism**.

**Получит ли получатель ровно один раз?**
- **Нет**, exactly-once в distributed системе недостижим. Возможны дубликаты.
- Снижаем через **dedupe**: при приходе события проверяем **event ID**. Видели раньше: отбрасываем. Нет: отправляем.

### Дополнительные компоненты

- **Notification template**: преформатированное уведомление, в которое подставляются параметры, стили, tracking links. Плюсы: консистентный формат, меньше ошибок, экономия времени.
- **Notification settings**: пользователи хотят контроль. Таблица: `user_id`, `channel` (push/email/SMS), `opt_in` (boolean). **Перед отправкой проверяем opt-in**.
- **Rate limiting**: ограничиваем число уведомлений на юзера, иначе он отключит их полностью.
- **Retry mechanism**: при неудаче third-party уведомление возвращается в очередь. Если проблема сохраняется, **alert разработчикам**.
- **Security**: `appKey` и `appSecret` защищают push API. Отправлять могут только аутентифицированные клиенты.
- **Monitor queued notifications**: ключевая метрика, **число сообщений в очередях**. Растёт, значит workers не успевают, добавляем workers.
- **Events tracking**: open rate, click rate, engagement. Интеграция с **analytics service**.

### Итоговый дизайн

К improved design добавлено:
- В notification servers: **authentication** и **rate limiting**.
- **Retry mechanism** с возвратом в очередь и ограниченным числом попыток.
- **Templates**.
- **Monitoring и tracking**.

## Step 4. Wrap up

Что подчеркнуть:
- **Message queues** для decoupling
- **Reliability**: retry, notification log, dedupe
- **Security**: appKey/appSecret
- **Tracking и monitoring** на каждом этапе
- **Respect user settings**: проверка opt-in
- **Rate limiting** (frequency capping)

## Шпаргалка на интервью

1. Уточни: типы, soft real-time, устройства, триггеры, opt-out, объём (10M push, 1M SMS, 5M email).
2. Объясни каналы: **APNS** (iOS), **FCM** (Android), **Twilio/Nexmo** (SMS), **Sendgrid/Mailchimp** (email).
3. Contact info: таблицы user и device, у юзера много устройств.
4. Initial design и его проблемы: **SPOF, scaling, bottleneck**.
5. Improved: вынести DB/cache, горизонтальное масштабирование, **очередь на каждый канал**, workers.
6. Reliability: **notification log + retry**, **dedupe по event ID**, exactly-once не бывает.
7. Дополнения: templates, settings (opt-in), rate limiting, security, monitoring очередей, tracking.
8. Extensibility third-party: легко заменить провайдера (пример с Китаем).
