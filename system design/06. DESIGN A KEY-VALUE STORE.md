# Design a Key-Value Store: конспект

## Что это

**Key-value store** это non-relational DB. Уникальный key, к нему value (string, list, object), которое обычно считается opaque. Ключ plain text или hash, короткий лучше для performance. Примеры: Dynamo, Memcached, Redis.

API: `put(key, value)` и `get(key)`.

## Требования (Step 1)

- Размер пары < 10 KB
- Big data
- **High availability**: быстро отвечает даже при failures
- **High scalability** и **automatic scaling** (серверы добавляются и удаляются по трафику)
- **Tunable consistency**
- **Low latency**

## Single server vs distributed

- Single server: hash table в памяти. Оптимизации: **compression** и хранить в памяти только hot data, остальное на disk. Всё равно быстро упрёшься в capacity.
- Для big data нужен **distributed key-value store** (по сути **distributed hash table**).

## CAP theorem (обязательно знать)

Нельзя одновременно получить больше двух из трёх:
- **Consistency**: все клиенты видят одни и те же данные, на какой бы node ни зашли.
- **Availability**: любой запрос получает ответ, даже если часть nodes упала.
- **Partition Tolerance**: система работает при разрыве связи между nodes.

Виды систем:
- **CP**: жертвуем availability.
- **AP**: жертвуем consistency.
- **CA**: в реальности **не существует**, потому что network partition неизбежен.

Пример с тремя replicas (n1, n2, n3), n3 отвалился от остальных:
- **CP**: блокируем writes на n1 и n2, чтобы не было inconsistency. Система недоступна для записи. Пример: банки, где баланс обязан быть актуальным, при inconsistency возвращается error.
- **AP**: n1 и n2 продолжают принимать reads/writes (reads могут вернуть stale data), а когда partition исчезнет, данные синхронизируются на n3.

Выбор CP или AP надо обсудить с интервьюером под use case.

## Компоненты (основано на Dynamo, Cassandra, BigTable)

### 1. Data partition

Задачи: равномерно распределить данные и минимизировать movement при add/remove nodes. Решение: **consistent hashing** (Chapter 5).

Плюсы:
- **Automatic scaling**.
- **Heterogeneity**: число virtual nodes пропорционально capacity сервера.

### 2. Data replication

- Реплицируем **асинхронно** на **N** серверов (N настраивается).
- Выбор: от позиции ключа идём по часовой стрелке и берём первые N серверов.
- С virtual nodes берём только **уникальные физические серверы**, иначе реплики могут оказаться на одной машине.
- Реплики размещаем в **разных data centers** (nodes в одном DC падают вместе: питание, сеть, катастрофы).

### 3. Consistency: quorum consensus

- **N**: число replicas.
- **W**: write quorum, сколько replicas должны подтвердить запись.
- **R**: read quorum, сколько replicas должны ответить на чтение.
- **W = 1 не значит, что данные записаны на один сервер.** Это значит, что coordinator ждёт минимум один ack. **Coordinator** это proxy между клиентом и nodes.
- Tradeoff между latency и consistency: W или R = 1 быстро, W или R > 1 consistency лучше, но ждём самую медленную replica.

Конфигурации:
| Условие | Результат |
|---|---|
| R = 1, W = N | оптимизировано под быстрое чтение |
| W = 1, R = N | оптимизировано под быструю запись |
| **W + R > N** | **strong consistency** (обычно N=3, W=R=2), есть пересечение с node, у которой свежие данные |
| W + R ≤ N | strong consistency не гарантируется |

### Consistency models

- **Strong**: read всегда возвращает результат последней записи.
- **Weak**: read может не увидеть последнее значение.
- **Eventual** (вид weak): через какое-то время все replicas сходятся.

Strong обычно требует блокировать операции, пока все replicas не согласились, что плохо для high availability. **Dynamo и Cassandra используют eventual consistency**, её и рекомендуют. При concurrent writes в систему попадают конфликтующие значения, и клиент должен их reconcile.

### 4. Inconsistency resolution: versioning и vector clock

- **Versioning**: каждое изменение это новая **immutable** версия.
- Пример конфликта: две node одновременно меняют name на «johnSanFrancisco» и «johnNewYork». Это две конфликтующие версии v1 и v2.
- **Vector clock**: пары `[server, version]` у data item, `D([S1, v1], [S2, v2], ...)`. При записи на сервер Si: если `[Si, vi]` есть, инкрементируем vi, иначе создаём `[Si, 1]`.
- **Ancestor (нет конфликта)**: в vector clock Y все счётчики ≥ соответствующих в X. Пример: `([s0,1],[s1,1])` предок `([s0,1],[s1,2])`.
- **Sibling (конфликт)**: в Y есть счётчик меньше, чем в X. Пример: `([s0,1],[s1,2])` и `([s0,2],[s1,1])`.
- Пример из книги: D3([Sx,2],[Sy,1]) и D4([Sx,2],[Sz,1]) конфликтуют. Клиент reconcile'ит, и сервер записывает D5([Sx,3],[Sy,1],[Sz,1]).

**Минусы vector clocks:**
- Усложняют клиента: он реализует conflict resolution.
- Пары `[server: version]` быстро растут. Решение: **threshold** по длине, старые пары удаляются, но тогда нельзя точно определить descendant-отношения. В Dynamo с этим на практике не сталкивались.

### 5. Handling failures

**Failure detection**
- Одного источника недостаточно, нужно минимум **два независимых источника**, чтобы пометить сервер как down.
- **All-to-all multicasting**: просто, но неэффективно при большом числе серверов.
- **Gossip protocol** (децентрализованный, лучше):
  - Каждая node хранит **membership list** (member ID + heartbeat counter).
  - Периодически инкрементирует свой heartbeat.
  - Периодически шлёт heartbeats случайным nodes, те распространяют дальше.
  - Если heartbeat не растёт дольше заданного периода, member считается offline.
  - Остальные nodes подтверждают, после чего узел помечается down и информация распространяется.

**Temporary failures: sloppy quorum + hinted handoff**
- **Strict quorum** может блокировать операции.
- **Sloppy quorum**: берутся первые W healthy серверов для writes и первые R healthy для reads на ring, offline игнорируются.
- **Hinted handoff**: пока сервер недоступен, запросы временно обрабатывает другая node, а когда он возвращается, она отдаёт ему изменения.

**Permanent failures: anti-entropy + Merkle tree**
- **Anti-entropy protocol**: сравнивает данные на replicas и обновляет до новейшей версии.
- **Merkle tree (hash tree)**: каждый non-leaf node хранит hash от своих детей. Нужен для детекта inconsistency и минимизации передаваемых данных.
- Построение: 1) делим key space на buckets, 2) hash каждого ключа в bucket, 3) один hash на bucket, 4) строим дерево вверх до root.
- Сравнение: сравниваем root hashes. Совпали, данные одинаковые. Нет, идём вниз по левым и правым детям и находим несинхронизированные buckets.
- Объём синхронизации **пропорционален различиям**, а не размеру данных. Пример: 1M buckets на 1B keys, это 1000 keys на bucket.

**Data center outage**
- Реплицируем данные в **несколько data centers**, тогда при падении одного данные доступны через другие.

## Архитектура

- Клиент общается через `get(key)` и `put(key, value)`.
- **Coordinator** это proxy между клиентом и store.
- Nodes на ring через consistent hashing.
- **Полностью decentralized**: add/remove nodes автоматически.
- Данные реплицируются на несколько nodes.
- **Нет SPOF**: у всех nodes одинаковые обязанности.

## Write path (по Cassandra)

1. Запрос записывается в **commit log** (файл).
2. Данные пишутся в **memory cache**.
3. Когда cache заполнен или достиг threshold, данные flush'атся в **SSTable** на disk. SSTable это sorted list пар `<key, value>`.

## Read path

1. Проверяем memory cache. Есть: возвращаем клиенту.
2. Нет в памяти: проверяем **bloom filter**.
3. Bloom filter показывает, какие **SSTables** могут содержать ключ.
4. SSTable возвращает данные.
5. Результат возвращается клиенту.

## Шпаргалка на интервью

1. Уточни требования: размер пары, consistency vs availability.
2. Объясни **CAP**, выбери **AP + eventual consistency** (как Dynamo/Cassandra), CA в реальности нет.
3. Partition: **consistent hashing**, replication на N серверов по ring в разных DC.
4. Consistency: **N, W, R**, `W + R > N` для strong consistency.
5. Конфликты: **vector clocks**, назови их минусы.
6. Failures: **gossip**, **sloppy quorum + hinted handoff**, **Merkle tree**.
7. Архитектура: decentralized, coordinator, нет SPOF.
8. Write path: commit log, memory, SSTable. Read path: memory, bloom filter, SSTable.
