# Consistent Hashing: конспект

## Проблема: rehashing

- Наивный способ балансировки: `serverIndex = hash(key) % N`, где N это размер server pool.
- Работает, пока pool фиксирован и данные распределены равномерно.
- Если сервер добавили или убрали, N меняется, и **почти все ключи** переезжают на другие серверы, а не только ключи упавшего. Клиенты ходят не на тот сервер, и получается **storm of cache misses**.
- Пример: было 4 сервера, упал один, стало `% 3`, большинство ключей перераспределилось.

## Consistent hashing: идея

- При изменении размера hash table в среднем переезжает только **k/n ключей** (k это количество ключей, n это количество slots). В обычных hash tables переезжает почти всё.

### Как устроено

1. **Hash space**: пространство значений hash function. Для SHA-1 это от 0 до 2^160 − 1.
2. **Hash ring**: соединяем два конца hash space в кольцо.
3. **Hash servers**: хешируем server IP или имя той же функцией и кладём серверы на кольцо.
4. **Hash keys**: хешируем ключи на то же кольцо. Здесь **нет modulo**.
5. **Server lookup**: от позиции ключа идём **по часовой стрелке** до первого сервера. Он и хранит ключ.

### Добавление и удаление сервера

- **Add server**: переезжает только часть ключей. Новый сервер забирает ключи, которые раньше уходили на следующий за ним сервер по часовой. Остальные ключи остаются на местах.
- **Remove server**: только ключи удалённого сервера переезжают на следующий по часовой сервер. Остальные не затрагиваются.

## Две проблемы базового подхода

1. **Неравные partitions**: partition это hash space между соседними серверами. При добавлении или удалении серверов невозможно держать размеры одинаковыми. После удаления s1 partition у s2 может стать вдвое больше, чем у соседей.
2. **Неравномерное распределение ключей**: серверы могут оказаться на кольце так, что большинство ключей уйдёт на один сервер, а на других данных не будет вообще.

**Решение: virtual nodes (replicas).**

## Virtual nodes

- Каждый сервер представлен **несколькими виртуальными узлами** на кольце: вместо `s0` это `s0_0`, `s0_1`, `s0_2`. Сервер отвечает за много partitions.
- Lookup: идём по часовой до первого **virtual node**, он указывает на реальный сервер.
- Больше virtual nodes: меньше **standard deviation**, распределение ровнее. По эксперименту из книги: 100 virtual nodes дают отклонение ~10% от среднего, 200 дают ~5%.
- **Tradeoff**: больше virtual nodes требует больше памяти для метаданных. Число настраивается под требования системы.

## Find affected keys (частый вопрос)

- **Добавили сервер**: от нового узла идём **против часовой стрелки** до первого сервера. Ключи в этом диапазоне переезжают на новый сервер.
- **Удалили сервер**: от удалённого узла идём против часовой до первого сервера. Ключи в этом диапазоне переезжают на следующий по часовой сервер.

## Benefits (что сказать в конце)

- Минимум ключей переезжает при добавлении и удалении серверов.
- Легко **scale horizontally**: данные распределены равномернее.
- Смягчает **hotspot key problem** (celebrity problem): данные популярных ключей не попадают на один shard.

## Где используется

- Partitioning в **Amazon Dynamo**
- Data partitioning в **Apache Cassandra**
- **Discord**
- **Akamai CDN**
- **Maglev** network load balancer

## Шпаргалка на интервью

1. Проблема: `hash % N` ломается при смене N, почти все ключи переезжают, получаем storm of cache misses.
2. Решение: hash ring, серверы и ключи хешируются одной функцией, ключ идёт к первому серверу по часовой.
3. При add/remove переезжает только соседний диапазон (~k/n ключей).
4. Проблемы базового подхода: неравные partitions и неравномерное распределение ключей. Решаются **virtual nodes**.
5. Tradeoff virtual nodes: ровнее распределение против большего расхода памяти.
6. Назвать реальные системы: Dynamo, Cassandra.
