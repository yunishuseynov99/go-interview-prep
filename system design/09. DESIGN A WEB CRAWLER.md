# Design a Web Crawler: конспект

## Что это

**Web crawler** (robot, spider) стартует с нескольких страниц и идёт по ссылкам, собирая новый контент.

**Use cases:**
- **Search engine indexing** (основной, Googlebot)
- **Web archiving** (библиотеки, архивы)
- **Web mining** (например, финфирмы качают annual reports)
- **Web monitoring** (поиск нарушений copyright и trademark)

**Базовый алгоритм:** скачать страницы по набору URL → извлечь из них URL → добавить новые в очередь → повторять.

## Step 1. Requirements

- Цель: **search engine indexing**
- **1 млрд страниц в месяц**
- Только **HTML**
- Учитываем новые и изменённые страницы
- Хранить HTML **до 5 лет**
- Страницы с **дублирующимся контентом игнорируем**

**Характеристики хорошего crawler (обязательно назвать):**
- **Scalability**: параллелизация
- **Robustness**: bad HTML, зависшие серверы, crashes, malicious links
- **Politeness**: не заваливать сайт запросами
- **Extensibility**: легко добавлять новые типы контента

## Back-of-the-envelope

- QPS = 1B / 30 / 24 / 3600 ≈ **400 страниц/сек**
- Peak QPS = 2 × QPS = **800**
- Средняя страница 500 KB: 1B × 500 KB = **500 TB в месяц**
- За 5 лет: 500 TB × 12 × 5 = **30 PB**

## Step 2. High-level design: компоненты

- **Seed URLs**: точка старта. Для всего web делим URL space по **locality** (страны) или по **topics** (shopping, sports, healthcare).
- **URL Frontier**: хранит URL, которые ещё надо скачать (по сути FIFO queue).
- **HTML Downloader**: скачивает страницы по URL из Frontier.
- **DNS Resolver**: переводит URL в IP.
- **Content Parser**: парсит и валидирует страницу (malformed pages создают проблемы). Вынесен в отдельный компонент, чтобы не тормозить crawl.
- **Content Seen?**: детект дубликатов (около 29% web дублируется). Сравниваем **hash** страниц, а не символы.
- **Content Storage**: большая часть на **disk**, популярный контент в **memory** для низкой latency.
- **URL Extractor**: достаёт ссылки, относительные пути превращает в абсолютные.
- **URL Filter**: отсекает ненужные типы контента, расширения, error links, blacklisted сайты.
- **URL Seen?**: что уже посещали или уже в Frontier. Защита от лишней нагрузки и бесконечных циклов. Реализация: **bloom filter** или **hash table**.
- **URL Storage**: хранит посещённые URL.

## Workflow (11 шагов)

1. Seed URLs → URL Frontier
2. HTML Downloader берёт URL из Frontier
3. Получает IP у DNS Resolver, скачивает
4. Content Parser парсит и проверяет на malformed
5. Передача в **Content Seen?**
6. Уже есть в storage: страница **отбрасывается**. Нет: идёт дальше в Link Extractor
7. Link Extractor достаёт ссылки
8. Ссылки идут в URL Filter
9. Затем в **URL Seen?**
10. Уже обработан: ничего не делаем
11. Новый: добавляем в URL Frontier

## Step 3. Deep dive

### DFS vs BFS

- Web это **directed graph** (страницы = nodes, ссылки = edges).
- **DFS** обычно не подходит: глубина может быть огромной.
- **BFS** (FIFO queue) стандарт, но у него две проблемы:
  1. Большинство ссылок ведут на тот же host, crawler забивает один сервер (**impolite**).
  2. Не учитывает **priority**: страницы разного качества и важности.

### URL Frontier (ключевой компонент)

Обеспечивает **politeness**, **prioritization** и **freshness**.

**Politeness**
- Идея: **одна страница за раз с одного host**, между загрузками добавляем delay.
- Компоненты:
  - **Queue router**: следит, чтобы каждая очередь содержала URL только одного host.
  - **Mapping table**: host → queue.
  - **FIFO queues b1...bn**: у каждой URL одного host.
  - **Queue selector**: привязывает worker thread к очереди.
  - **Worker threads 1..N**: качают страницы одного host по очереди с delay.

**Priority**
- Пример: Apple home page важнее случайного поста на форуме про Apple.
- Приоритет по **PageRank**, трафику сайта, частоте обновлений.
- Компоненты:
  - **Prioritizer**: считает приоритет URL.
  - **Queues f1...fn**: у каждой свой приоритет, высокоприоритетные выбираются с большей вероятностью.
  - **Queue selector**: случайный выбор с перекосом в сторону высокого приоритета.
- Итоговый Frontier: **Front queues** (prioritization) + **Back queues** (politeness).

**Freshness**
- Страницы постоянно меняются, нужен периодический **recrawl**. Полный recrawl слишком дорог, поэтому:
  - recrawl по **истории обновлений** страницы;
  - **важные страницы** перекачиваем чаще.

**Storage для Frontier**
- Сотни миллионов URL: только memory не durable и не scalable, только disk слишком медленный.
- **Hybrid**: большинство на disk, **buffers в memory** для enqueue/dequeue, периодически сбрасываются на disk.

### HTML Downloader

**Robots.txt (Robots Exclusion Protocol)**
- Стандарт, по которому сайт говорит crawler'ам, что можно качать. Перед crawl проверяем и соблюдаем правила.
- Результат **кэшируем**, периодически обновляем.

**Performance optimization (4 пункта)**
1. **Distributed crawl**: задачи на много серверов, на каждом много threads, URL space разбит на части.
2. **Cache DNS Resolver**: DNS это bottleneck (ответ 10–200 ms, часто синхронный, остальные threads блокируются). Свой DNS cache (domain → IP), обновляется **cron jobs**.
3. **Locality**: crawl servers географически ближе к хостам. Касается и cache, queue, storage.
4. **Short timeout**: не отвечает за заданное время, бросаем и идём дальше.

### Robustness

- **Consistent hashing** для распределения нагрузки между downloaders (Chapter 5).
- **Save crawl states and data**: упавший crawl можно перезапустить с сохранённого состояния.
- **Exception handling**: не падать из-за ошибок.
- **Data validation**.

### Extensibility

- Новые модули подключаются как plug-in. Примеры: **PNG Downloader**, **Web Monitor** (для copyright и trademark).

### Проблемный контент

1. **Redundant content**: около 30% дубликатов, детектим по **hash или checksum**.
2. **Spider traps**: страницы, из-за которых crawler зацикливается (например, `/foo/bar/foo/bar/...`).
   - Ограничение **максимальной длины URL**.
   - Универсального решения нет. Признак: аномально много страниц на одном сайте. Такие сайты проверяют вручную и исключают или добавляют кастомные URL filters.
3. **Data noise**: реклама, code snippets, spam URL. Исключаем.

## Step 4. Wrap up: что добавить

- **Server-side rendering (dynamic rendering)**: ссылки, сгенерированные JavaScript/AJAX, не видны без рендеринга.
- **Anti-spam** компонент для фильтрации низкокачественных и spam страниц.
- **Database replication и sharding**.
- **Horizontal scaling**: сотни и тысячи серверов, главное держать их **stateless**.
- **Availability, consistency, reliability** (Chapter 1).
- **Analytics**.

## Шпаргалка на интервью

1. Уточни: цель (search indexing), объём (1B/мес), типы контента (HTML), свежесть, хранение (5 лет), дубликаты.
2. Назови 4 свойства: **scalability, robustness, politeness, extensibility**.
3. Оценка: **400 QPS, peak 800, 500 TB/мес, 30 PB за 5 лет**.
4. Назови компоненты: Seed URLs → **URL Frontier** → HTML Downloader (+ DNS) → Content Parser → **Content Seen?** → URL Extractor → URL Filter → **URL Seen?** → Frontier.
5. **BFS** (FIFO), объясни две его проблемы и как Frontier их решает: **politeness** (очередь на host + delay) и **priority** (front/back queues).
6. Freshness: recrawl по истории и приоритету. Frontier storage: hybrid disk + memory buffers.
7. Downloader: **robots.txt**, distributed crawl, **DNS cache**, locality, short timeout.
8. Проблемный контент: дубликаты (hash), **spider traps** (лимит длины URL, ручная проверка), noise.
9. Wrap up: server-side rendering, anti-spam, scaling, analytics.
