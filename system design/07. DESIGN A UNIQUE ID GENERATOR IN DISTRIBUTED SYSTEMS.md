# Design a Unique ID Generator: конспект

## Зачем и почему не auto_increment

- `auto_increment` в обычной DB не работает в distributed среде: один сервер не вытянет нагрузку, а генерировать уникальные ID через несколько DB с минимальной задержкой сложно.

## Step 1. Requirements

- IDs **уникальные**
- Только **numerical**
- Влезают в **64 bit**
- **Упорядочены по времени** (вечерние больше утренних, не обязательно +1)
- **10 000+ ID в секунду**

## Step 2. Варианты (надо уметь сравнить)

**1. Multi-master replication**
- Используем `auto_increment`, но шаг равен **k** (число DB серверов), а не 1.
- Минусы: тяжело масштабировать на несколько data centers, ID **не растут со временем** между серверами, плохо при add/remove серверов.

**2. UUID**
- 128-bit число, генерируется независимо на каждом web server, **без координации**. Вероятность коллизии ничтожна.
- Плюсы: просто, нет synchronization issues, легко scale.
- Минусы: **128 bit** (нужно 64), **не растёт со временем**, может быть не numeric.

**3. Ticket server** (Flickr)
- Один централизованный сервер с `auto_increment`.
- Плюсы: numeric, просто, подходит для small/medium scale.
- Минус: **SPOF**. Несколько ticket servers создают проблему data synchronization.

**4. Twitter Snowflake** (выбираем его)
- **Divide and conquer**: ID делится на секции, ID не генерируется "целиком".

## Snowflake: структура 64-bit ID

| Секция | Bits | Описание |
|---|---|---|
| Sign bit | 1 | Всегда 0, резерв на будущее |
| Timestamp | 41 | Миллисекунды с epoch (default Twitter: Nov 04, 2010) |
| Datacenter ID | 5 | 2^5 = 32 data centers |
| Machine ID | 5 | 2^5 = 32 машины на DC |
| Sequence number | 12 | +1 на каждый ID на машине, **сбрасывается в 0 каждую миллисекунду** |

## Step 3. Deep dive

- **Datacenter ID и machine ID** выбираются при старте и обычно фиксированы. Случайное изменение приводит к **ID conflicts**, поэтому любые изменения требуют review.
- **Timestamp** (самые старшие биты) растёт со временем, поэтому ID **sortable by time**.
  - Максимум 2^41 − 1 мс ≈ **69 лет**. Custom epoch ближе к текущей дате отодвигает overflow. Потом нужен новый epoch или миграция ID.
- **Sequence number**: 12 bit, 2^12 = **4096** комбинаций. Равен 0, если в мс на сервере генерируется один ID. Теоретически одна машина даёт до **4096 ID в мс**.

## Step 4. Wrap up: что добавить

- **Clock synchronization**: дизайн предполагает одинаковые часы на серверах. Это не всегда верно (multi-core, multi-machine). Решение: **NTP (Network Time Protocol)**.
- **Section length tuning**: для low concurrency и long-term систем лучше меньше bits на sequence и больше на timestamp.
- **High availability**: ID generator mission-critical, должен быть highly available.

## Сравнение подходов

| Подход | Numeric | 64 bit | Sortable by time | SPOF / координация |
|---|---|---|---|---|
| Multi-master | да | да | нет (между серверами) | плохо масштабируется |
| UUID | не всегда | нет (128) | нет | нет координации |
| Ticket server | да | да | да | **SPOF** |
| Snowflake | да | да | да | нет координации |

## Шпаргалка на интервью

1. Уточни: unique, numeric, 64-bit, sortable by time, 10k+ ID/sec.
2. Назови 4 варианта и их минусы (multi-master, UUID, ticket server).
3. Выбери **Snowflake** и нарисуй раскладку: 1 + 41 + 5 + 5 + 12.
4. Объясни: timestamp даёт sortability, sequence решает коллизии внутри мс, datacenter/machine ID разводят генераторы.
5. Числа: 69 лет, 32 DC × 32 машины, 4096 ID/мс на машину.
6. Wrap up: **clock sync (NTP)**, tuning длины секций, high availability.
