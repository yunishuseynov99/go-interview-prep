### 21. Выравнивание памяти (Memory Alignment)

**Вопрос:** Какая из этих структур займет меньше памяти и почему? (Архитектура 64-bit).

```go
type A struct {
    x bool
    y float64
    z bool
}

type B struct {
    y float64
    x bool
    z bool
}
```

**Ответ:** Структура `B` займет меньше места.

**Почему:** Из-за выравнивания (alignment). На 64-битной архитектуре слово равно 8 байтам.
*   **Struct A:** `bool` (1 байт) + *padding* (7 байт) + `float64` (8 байт) + `bool` (1 байт) + *padding* (7 байт). Итого: **24 байта**.
*   **Struct B:** `float64` (8 байт) + `bool` (1 байт) + `bool` (1 байт) + *padding* (6 байт). Итого: **16 байт**.
Компилятор добавляет паддинг, чтобы поля располагались по адресам, кратным размеру их типа (или машинного слова), для оптимизации доступа к памяти. В Go порядок полей имеет значение для потребления памяти.

### 22. Preemption (Вытеснение горутин)

**Вопрос:** Зависнет ли программа в Go 1.13 и в Go 1.14+?

```go
func main() {
    runtime.GOMAXPROCS(1)
    go func() {
        for {
            // Пустой цикл без вызовов функций
        }
    }()
    
    time.Sleep(time.Second)
    fmt.Println("Done")
}
```

**Ответ:**
*   **Go < 1.14:** Зависнет навсегда.
*   **Go >= 1.14:** Выведет "Done".

**Почему:**
В старых версиях планировщик Go был кооперативным. Переключение контекста происходило только на вызовах функций, аллокациях или сетевых вызовах. Плотный математический цикл блокировал процессор (P).
С версии 1.14 внедрено **асинхронное вытеснение (asynchronous preemption)** на основе сигналов ОС (SIGURG). Теперь планировщик может принудительно прервать даже плотный цикл спустя ~10мс.

### 23. Сравнение интерфейсов с функциями

**Вопрос:** Что произойдет при выполнении?

```go
type FuncContainer interface {
    Run()
}

type Wrapper struct {
    action func()
}
func (w Wrapper) Run() { w.action() }

func main() {
    var a, b FuncContainer
    a = Wrapper{action: func() {}}
    b = Wrapper{action: func() {}}
    
    if a == b {
        fmt.Println("Equal")
    }
}
```

**Ответ:** Паника в рантайме (`panic: runtime error: comparing uncomparable type`).

**Почему:** Интерфейсы можно сравнивать оператором `==`, если их динамические типы (dynamic types) сравнимы. Структура `Wrapper` содержит поле типа `func`. Функции в Go **несравнимы** (их можно сравнивать только с `nil`).
Если интерфейс содержит внутри несравнимый тип (slice, map, func), попытка сравнения вызывает панику, а не ошибку компиляции.

### 24. Утечка памяти через time.After

**Вопрос:** Почему этот код может вызвать утечку памяти при высокой нагрузке, и как это исправить?

```go
func worker(ch <-chan int) {
    for {
        select {
        case msg := <-ch:
            // process msg
        case <-time.After(time.Second):
            // timeout logic
        }
    }
}
```

**Ответ:** `time.After` создает таймер, который не собирается сборщиком мусора до тех пор, пока не "выстрелит" (истечет время), даже если `select` выбрал другой кейс (`msg := <-ch`).
Если сообщения приходят очень часто (например, 1000 RPS), а таймаут длинный (1 сек), вы будете создавать тысячи таймеров в секунду, которые будут висеть в памяти.

**Решение:** Использовать `time.NewTimer` и останавливать его вручную:
```go
timer := time.NewTimer(time.Second)
defer timer.Stop()
// ... внутри цикла сброс timer.Reset(...)
```

### 25. Рост слайса (Slice Growth Strategy)

**Вопрос:** У нас есть слайс `s` емкостью (capacity) 1000 элементов. Мы делаем `append`. Какой будет новая емкость?
A) 1250
B) 2000
C) Зависит от версии Go

**Ответ:** С) Зависит от версии, но в современных (1.18+) формула сложнее.

**Почему:**
*   Раньше (до 1.18): Если `cap < 1024`, то удвоение (x2). Если `cap >= 1024`, то рост на ~25% (x1.25).
*   Сейчас (Go 1.18+): Формула сглажена. Переход от x2 к меньшим коэффициентам происходит более плавно. Для 1000 элементов рост будет все еще близок к x2 или чуть меньше, но для больших массивов коэффициент стремится к 1.25 быстрее.
*На собеседовании важно знать, что правило "удвоения" перестает работать после определенного порога (раньше 1024), чтобы экономить память.*

### 26. Sync.Pool и GC

**Вопрос:** Вы положили объект в `sync.Pool`. Гарантировано ли, что он будет там при следующем вызове `Get`?

**Ответ:** Нет.

**Почему:** `sync.Pool` очищается при **каждом** запуске сборщика мусора (GC).
Если между `Put` и `Get` прошел GC, пул будет пуст, и `Get` вернет результат вызова функции `New` (если она задана) или `nil`.
`sync.Pool` предназначен для снижения нагрузки на аллокатор (reuse), а не для долгосрочного кэширования (для этого нужен LRU cache).

### 27. RWMutex Writer Starvation

**Вопрос:** Может ли множество читателей (`RLock`) заблокировать писателя (`Lock`) навсегда?

```go
var mu sync.RWMutex
// Горутины постоянно вызывают mu.RLock() -> mu.RUnlock()
// Другая горутина вызывает mu.Lock()
```

**Ответ:** Нет (в Go).

**Почему:** Реализация `sync.RWMutex` в Go предотвращает "голодание писателя" (Writer Starvation).
Если писатель вызвал `Lock()`, новые читатели, пытающиеся вызвать `RLock()`, будут заблокированы, даже если другие читатели сейчас держат замок. Писатель ждет завершения *текущих* читателей, но *новые* читатели ждут писателя.

### 28. JSON Marshal и Map Order

**Вопрос:** Гарантируется ли порядок ключей в JSON при маршалинге `map`?

```go
m := map[string]int{"a": 1, "b": 2, "c": 3}
b, _ := json.Marshal(m)
```

**Ответ:** Да, в итоговом JSON ключи будут отсортированы по алфавиту.

**Почему:** Хотя итерация по `map` в Go рандомна, `encoding/json` специально сортирует ключи перед сериализацией. Это сделано для детерминированности тестов и хеш-сумм получаемых байтов. Если вы запустите этот код 10 раз, результат будет одинаковый (например, `{"a":1,"b":2,"c":3}`).

### 29. String to Byte Slice (Zero Copy)

**Вопрос:** Как преобразовать `string` в `[]byte` без выделения памяти (аллокации) и копирования данных? Безопасно ли это?

**Ответ:** Можно использовать `unsafe` (или с Go 1.20 `unsafe.String` / `unsafe.Slice`).

```go
func strToBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
```

**Безопасно ли?** Нет, это опасно.
Строки в Go неизменяемы (immutable). Полученный таким образом слайс байт указывает на ту же память, где лежит строка. Если вы попытаетесь изменить этот слайс (`b[0] = 'z'`), вы можете получить **Segmentation Fault** (если память лежит в read-only сегменте бинарника) или вызвать непредсказуемое поведение программы, изменив "константу" в других частях кода.

### 30. Nil Channel в Select

**Вопрос:** Зачем программисты иногда явно присваивают каналу `nil` внутри цикла с `select`?

```go
for {
    select {
    case x, ok := <-ch1:
        if !ok {
            ch1 = nil // <--- Зачем?
        } else {
            // handle x
        }
    case x, ok := <-ch2:
       // ...
    }
}
```

**Ответ:** Чтобы "отключить" этот case в `select`.

**Почему:** Чтение из `nil` канала блокирует горутину навсегда. В конструкции `select`, если один из каналов равен `nil`, этот `case` просто игнорируется, и `select` слушает остальные каналы.
Если бы мы не занулили канал после его закрытия (`!ok`), `select` на следующей итерации снова выбрал бы этот закрытый канал (так как чтение из закрытого канала возвращает zero-value мгновенно), что привело бы к бесконечному "горячему" циклу (busy loop) с нулями.
