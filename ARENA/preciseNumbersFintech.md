Это критически важный вопрос для финтеха. Одна ошибка в выборе типа данных может стоить компании миллионов (и проблем с аудиторами).

# Мой ответ: «Хранение денег и точных значений в Go»

Главное правило финтеха: **Никогда не используйте `float32` или `float64` для денег.**
Компьютеры используют двоичную систему счисления, и числа вроде `0.1` или `0.2` в ней нельзя представить точно. Результат `0.1 + 0.2` может быть `0.30000000000000004`. В масштабах банковских транзакций это приведет к "исчезновению" или "появлению" копеек.

В Go есть три основных стратегии для работы с точными значениями:

### 1. Integer Math (Целые числа / Микрониты) — Самый быстрый способ

Мы храним деньги в **минимальных неделимых единицах** (центах, копейках или милли-копейках).

*   **Реализация:** `int64`.
*   **Пример:** Вместо `$10.50` мы храним `1050` (центов). Или даже `10500000` (микро-долларов), если нужна высокая точность при конвертации валют.
*   **Плюсы:**
    *   **Скорость:** Это нативные процессорные инструкции. Операции занимают наносекунды.
    *   **Память:** Не требует аллокаций в куче (хранится на стеке).
    *   **Атомики:** Можно использовать `sync/atomic` для счетчиков баланса.
*   **Минусы:**
    *   Нужно всегда помнить о множителе (scale factor). Легко ошибиться, сложив доллары с иенами.
    *   Сложности при делении (нужно решать, как округлять остаток).

> **Вердикт:** Идеально для высоконагруженных систем, биллинга, подсчета балансов.

### 2. Библиотека `shopspring/decimal` — Де-факто стандарт

Если мы пишем бизнес-логику (расчет процентов по кредиту, инвойсы), `int64` становится неудобным. В Go стандартом индустрии является библиотека **`github.com/shopspring/decimal`**.

*   **Реализация:** Под капотом она использует `big.Int` (произвольная точность) + `exponent` (экспонента).
*   **Пример:**
    ```go
    price := decimal.NewFromFloat(19.99)
    quantity := decimal.NewFromInt(3)
    total := price.Mul(quantity) // Точно 59.97
    ```
*   **Плюсы:**
    *   **Immutable:** Операции возвращают новый объект, что безопасно.
    *   **Удобство:** Есть готовые методы `Round`, `Floor`, `Ceil`.
    *   **Сериализация:** Отлично работает с JSON (маршалится в строку, чтобы JS на фронтенде не округлил) и SQL (`driver.Valuer` для типа `DECIMAL`).
*   **Минусы:**
    *   Медленнее, чем `int64` (аллокации в куче).
    *   Внешняя зависимость.

> **Вердикт:** Лучший выбор для большинства бизнес-задач.

### 3. `math/big` (Rat/Int) — Стандартная библиотека

В стандартной библиотеке есть пакет `math/big`. Для денег теоретически подходит `big.Rat` (рациональные дроби, хранит числитель и знаменатель).

*   **Пример:** 1/3 хранится именно как 1 и 3, без потери точности.
*   **Почему это плохой выбор (обычно):**
    *   **Ужасный API:** Он мутабельный и громоздкий (`z.Add(x, y)` перезаписывает `z`).
    *   **Память:** Очень тяжелый.
    *   Сложно сохранять в базу данных (нужно конвертировать).

> **Вердикт:** Используем только для **очень сложной математики** (криптография, сложные деривативы), где нужна произвольная точность выше, чем позволяет `decimal`.

### Архитектурный паттерн: Структура Money

В серьезном проекте я бы не использовал "голый" `int64` или `decimal`. Я бы обернул это в свою структуру **Money**:

```go
type Money struct {
    Amount   int64  // или decimal.Decimal
    Currency string // "USD", "EUR"
}
```

Это защищает от глупых ошибок, вроде сложения 100 рублей и 10 долларов. Методы `Add` и `Sub` должны проверять валюту и паниковать или возвращать ошибку при несовпадении.

### Хранение и передача (Database & API)

1.  **База данных (PostgreSQL):**
    *   Всегда используем тип **`NUMERIC`** или **`DECIMAL`**.
    *   Никогда `REAL`, `FLOAT` или `DOUBLE PRECISION`.
    *   Если используем подход с `int64`, можно хранить как `BIGINT`, но тогда в коде нужно жестко контролировать множитель.

2.  **JSON (API):**
    *   Передаем деньги **только как СТРОКУ** (`"amount": "10.50"`).
    *   Если передать числом (`10.50`), фронтенд (JavaScript) преобразует его в float, и точность пропадет еще до того, как пользователь увидит цену.

### Резюме для интервью

> "Для хранения денег в Go **float — это табу**.
>
> Для **высоконагруженных систем** и простых балансов я выберу **`int64`** (микрониты), так как это нативно и быстро.
>
> Для **сложной бизнес-логики** я возьму **`shopspring/decimal`**, так как это стандарт индустрии с удобным API и корректной сериализацией.
>
> В базе данных я буду использовать только **`DECIMAL/NUMERIC`**, а по API отдавать значения в виде **строк**, чтобы избежать потерь точности на клиенте."
