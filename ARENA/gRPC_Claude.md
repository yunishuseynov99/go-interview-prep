## Как строить ответ

Хороший ответ на интервью — это «воронка»: 20 секунд на определение, потом углубление, потом сравнение и trade-off'ы. Интервьюер обычно останавливает вас там, где ему интересно.

---

### 1. Определение (10–20 секунд)

> gRPC — это фреймворк для удалённого вызова процедур от Google. Контракт описывается в `.proto`-файле на языке Protocol Buffers, из него кодогенерацией получаются клиентские и серверные стабы. Транспорт — HTTP/2, сериализация — бинарный protobuf. Основной сценарий — межсервисное взаимодействие внутри инфраструктуры, особенно в polyglot-окружении.

Это contract-first подход: сначала схема, потом код. И схема — единственный источник правды для всех языков.

### 2. Что под капотом

**Protocol Buffers.** Бинарный формат, поля кодируются по номеру (tag), а не по имени → компактнее JSON в разы и парсится значительно быстрее (нет разбора строк, нет аллокаций на ключи). Номера полей дают эволюцию схемы: старый клиент просто игнорирует неизвестные поля, новый видит дефолты вместо отсутствующих. Отсюда правило — **номера полей никогда не переиспользуются**, удалённые помечаются `reserved`.

**HTTP/2 как транспорт.** Это не «просто чтобы было»:
- **мультиплексирование** — много параллельных RPC в одном TCP-соединении, без head-of-line blocking на уровне приложения;
- **бинарные фреймы** — из них естественно вырастает стриминг;
- **HPACK** — сжатие заголовков, что важно при большом числе мелких вызовов;
- **long-lived соединение** — нет накладных расходов на TLS-хендшейк на каждый запрос.

**Четыре типа вызовов** — это то, что чаще всего спрашивают дальше:
| Тип | Описание | Пример |
|---|---|---|
| Unary | запрос → ответ | обычный CRUD |
| Server streaming | запрос → поток ответов | подписка на обновления, выгрузка большого списка |
| Client streaming | поток запросов → ответ | загрузка чанками, батчинг метрик |
| Bidirectional | оба потока независимо | чат, телеметрия, long-lived сессии |

**Что ещё даёт фреймворк из коробки** (здесь обычно видно senior'а):
- **Deadlines вместо таймаутов.** Клиент задаёт абсолютный дедлайн, и он *распространяется* по цепочке вызовов. Сервис A вызвал B, у A осталось 200 мс — B узнает об этом и не будет молотить 5 секунд. Плюс автоматическая отмена (cancellation propagation).
- **Metadata** — аналог заголовков, key-value, туда кладут трейсинг, авторизацию.
- **Interceptors** — middleware для логирования, метрик, аутентификации, ретраев.
- **Свои status-коды** (`OK`, `NOT_FOUND`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `RESOURCE_EXHAUSTED`…), не HTTP-коды. HTTP/2 тут — деталь транспорта.
- **Channel** — абстракция над пулом соединений с клиентской балансировкой (pick_first / round_robin) и service config: retry policy, hedging, backoff.

### 3. Сравнение с REST

Ключевая мысль: сравнивать надо не «быстро/медленно», а по модели взаимодействия.

- **Контракт.** У gRPC он обязателен и машиночитаем; у REST — опционален (OpenAPI, который часто расходится с реальностью). Это главное преимущество, а не производительность.
- **Формат.** Бинарь против текста: выигрыш в размере и CPU, проигрыш в читаемости.
- **Стриминг.** У gRPC первоклассный, двунаправленный. В REST приходится городить SSE, WebSocket или long-polling.
- **Кэширование.** REST поверх HTTP-семантики кэшируется прокси, CDN, браузером. gRPC — нет, всё POST-подобное, кэш надо делать руками.
- **Браузер.** Напрямую gRPC из браузера не работает: нет доступа к HTTP/2-фреймам из JS. Нужен gRPC-Web и прокси (Envoy) — это ограничение стоит назвать самому.

### 4. Минусы — обязательно назвать сами

Если кандидат перечисляет только плюсы, это красный флаг.

- **Отладка.** Нельзя сделать `curl` и глазами прочитать тело. Нужны `grpcurl`, reflection API, специальные плагины к снифферам.
- **Балансировка нагрузки.** Самая частая продовая боль: соединения долгоживущие, поэтому L4-балансировщик (в том числе обычный `Service` в Kubernetes) прибьёт весь трафик к одному поду. Нужна клиентская балансировка через headless service, либо L7-прокси / service mesh.
- **Публичные API.** Для внешних потребителей и партнёров REST/JSON остаётся дефолтом: ниже порог входа, работает из любого окружения.
- **Кодогенерация в пайплайне.** Нужно где-то хранить `.proto`, версионировать, линтить (buf), следить за обратной совместимостью.
- **Порог входа** выше, чем «отправить JSON».

### 5. Финальный вывод

> gRPC я бы выбрал для внутреннего межсервисного трафика, особенно если сервисов много, они на разных языках, важна латентность или нужен стриминг. Для публичного API и всего, что потребляет браузер, оставил бы REST — либо отдавал бы gRPC наружу через gRPC-Gateway, генерирующий REST-фасад из того же `.proto`.
