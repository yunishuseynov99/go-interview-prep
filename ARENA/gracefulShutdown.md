Это отличный вопрос, так как в продакшене без graceful shutdown (плавного завершения) мы теряем данные, обрываем соединения клиентов и получаем алерты от систем мониторинга.

# Мой ответ на собеседовании: «Расскажи про Graceful Shutdown»

**Graceful Shutdown** — это механизм корректной остановки приложения, при котором мы не просто «убиваем» процесс, а даем ему время доделать текущую работу.

В Go это стандартная практика, которая решает три задачи:
1. **Перестать принимать новые запросы.**
2. **Дождаться завершения уже начатых запросов** (in-flight requests).
3. **Корректно закрыть соединения** с базой данных, брокерами сообщений и файлами.

---

### Как это реализуется технически

Весь процесс строится на взаимодействии **каналов**, пакета **`os/signal`** и методов **`Shutdown`** (у HTTP-сервера) или **`Context`**.

Стандартный алгоритм выглядит так:

1. **Запуск сервера в горутине.** Мы не блокируем `main` вызовом `ListenAndServe`, чтобы иметь возможность слушать сигналы ОС.
2. **Подписка на сигналы.** Используем `signal.Notify`, чтобы перехватывать `SIGINT` (Ctrl+C) и `SIGTERM` (Docker/K8s stop).
3. **Блокировка Main.** Главная горутина ждёт сообщения из канала сигналов.
4. **Процесс остановки.** Когда сигнал получен:
   - Создаем `context.WithTimeout` (это наш дедлайн на остановку).
   - Вызываем `server.Shutdown(ctx)`.
   - Закрываем остальные ресурсы (БД, кеши).

### Пример кода (идиоматичный)

```go
func main() {
    // 1. Инициализация ресурсов
    db := initDB()
    srv := &http.Server{Addr: ":8080"}

    // 2. Запуск сервера в отдельной горутине
    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("listen: %s\n", err)
        }
    }()

    // 3. Подписка на сигналы ОС
    quit := make(chan os.Signal, 1) // Буферизированный канал!
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    
    // Блокируемся и ждем сигнала
    <-quit
    log.Println("Shutting down server...")

    // 4. Graceful Shutdown с таймаутом
    // Даем приложению 5 секунд на завершение дел
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    // Shutdown прекращает слушать порт, но ждет завершения обработчиков
    if err := srv.Shutdown(ctx); err != nil {
        log.Fatal("Server forced to shutdown:", err)
    }

    // 5. Закрытие ресурсов
    if err := db.Close(); err != nil {
        log.Printf("Error closing DB: %v", err)
    }

    log.Println("Server exiting")
}
```

---

### Важные нюансы, о которых стоит упомянуть

**1. Разница между `Close()` и `Shutdown()`**
Метод `srv.Close()` обрывает все соединения немедленно. Метод `srv.Shutdown(ctx)` делает это "нежно": он закрывает листенер (новые соединения не идут), но держит активные соединения открытыми, пока они не завершатся или пока не истечет контекст.

**2. Context Timeout (Hard limit)**
Таймаут в контексте обязателен. Если ваше приложение зависло при выходе (например, дедлок при записи в БД), оркестратор (Kubernetes) не будет ждать вечно. Обычно в K8s `terminationGracePeriodSeconds` по умолчанию 30 секунд. В коде мы ставим таймаут чуть меньше (например, 25 сек), чтобы успеть залогировать ошибку остановки до того, как K8s пошлет `SIGKILL`.

**3. Буферизированный канал для сигналов**
Канал `quit` должен иметь буфер `1`. Если сигнал придет ровно в момент старта приложения, но до того, как мы встали на `<-quit`, в небуферизированный канал записать не получится (никто не читает), и сигнал может быть пропущен (хотя `signal.Notify` старается не блокировать, лучше перестраховаться).

**4. Порядок закрытия**
Порядок важен: сначала останавливаем прием трафика (HTTP Server), ждем завершения хендлеров, и только потом закрываем базу данных. Если закрыть БД раньше, завершающиеся запросы упадут с ошибкой подключения.

**5. Background Workers**
Если в приложении есть фоновые воркеры (например, обработка очереди), для них нужно реализовать свой механизм отмены через `context.Done()` или закрытие канала задач, чтобы они тоже успели доделать работу.

---

### Резюме

> **Graceful shutdown — это стандарт качества production-кода.** В Go он реализуется через перехват сигналов `SIGTERM/SIGINT`, использование `http.Server.Shutdown()` для доработки текущих запросов и `context.WithTimeout` для гарантии того, что приложение всё-таки завершится, даже если что-то пойдет не так.
