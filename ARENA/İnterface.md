Отличный вопрос. Интерфейсы в Go — это основа полиморфизма и гибкой архитектуры. Это, пожалуй, вторая по важности тема после конкурентности.

Вот как я бы ответил на собеседовании, двигаясь от базы к внутрянке:

# Мой ответ на собеседовании: «Расскажи про Интерфейсы»

**Интерфейс в Go** — это **контракт поведения**. Он описывает набор методов, но не их реализацию.

В отличие от Java или C#, в Go реализация интерфейсов **неявная (implicit)**.
Это значит, что нам не нужно писать `implements MyInterface`. Если структура имеет все методы, описанные в интерфейсе, она *автоматически* его реализует. Это называется **Duck Typing** ("Если это выглядит как утка и крякает как утка — это утка").

---

### 1. Как это устроено под капотом (Runtime)

Это самая важная техническая часть. Интерфейс — это не просто указатель, это структура из двух машинных слов (двух полей):

1.  **Указатель на тип (Type Info):** Информация о том, какой конкретно тип лежит внутри (метаданные).
2.  **Указатель на данные (Data Pointer):** Ссылка на саму область памяти, где лежат данные конкретной структуры.

В Go есть два типа внутренних структур интерфейсов:

*   **`eface` (empty interface):** Для пустого интерфейса `interface{}` (или `any`). Хранит `_type` и `data`.
*   **`iface` (non-empty interface):** Для интерфейса с методами.
    *   Вместо простого типа он хранит **`itab`** (Interface Table).
    *   `itab` содержит кэшированную таблицу указателей на методы конкретного типа, чтобы вызов метода через интерфейс был быстрым (динамическая диспетчеризация).

---

### 2. Проблема nil interface (Классическая ловушка)

На собеседованиях часто показывают код: возвращаем `nil` указатель на структуру, принимаем его как интерфейс и проверяем `if i == nil`.

**Ответ:** Интерфейс равен `nil` только тогда, когда **И** тип, **И** значение равны `nil`.

```go
var s *MyStruct = nil
var i MyInterface = s

if i == nil {
    // Сюда мы НЕ попадем!
}
```
**Почему?** Потому что внутри интерфейса `i` записано: `(Type=*MyStruct, Value=nil)`. А чтобы интерфейс был `nil`, должно быть `(Type=nil, Value=nil)`.

---

### 3. Пустой интерфейс (`interface{}` или `any`)

Пустой интерфейс не содержит методов, поэтому ему удовлетворяет **любой** тип данных (int, string, struct, slice).
С Go 1.18 появился алиас **`any`**, который полностью эквивалентен `interface{}`.

Мы используем его, когда заранее неизвестен тип данных (например, `json.Unmarshal` или `fmt.Println`), но злоупотреблять им не стоит, так как мы теряем строгую типизацию.

---

### 4. Работа с интерфейсами (Type Assertion и Type Switch)

Чтобы "достать" конкретный тип из интерфейса, мы используем:

1.  **Type Assertion (Утверждение типа):**
    ```go
    val, ok := i.(int) // Пытаемся привести к int
    if ok { ... }
    ```
    Если не проверить `ok` и тип не совпадет — будет **panic**.

2.  **Type Switch:**
    ```go
    switch v := i.(type) {
    case int:
        // v имеет тип int
    case string:
        // v имеет тип string
    }
    ```

### 5. Best Practices (Как писать код)

На опыте я выделил два главных правила работы с интерфейсами в Go:

1.  **"Accept interfaces, return structs"** (Принимай интерфейсы, возвращай структуры).
    *   Функции должны требовать минимально необходимый интерфейс (гибкость для вызывающего).
    *   А возвращать лучше конкретный тип, чтобы не заставлять клиента гадать или приводить типы.

2.  **Маленькие интерфейсы (Interface Segregation Principle).**
    *   Лучше много интерфейсов по 1 методу (`io.Reader`, `io.Writer`), чем один огромный.
    *   Чем меньше интерфейс, тем мощнее абстракция (её проще реализовать).

---

### Резюме

> **Интерфейс в Go** — это способ описания поведения. Реализация неявная (Duck Typing).
> Под капотом это пара `(тип, значение)`. Это позволяет реализовать полиморфизм.
> Важно помнить про нюанс с `nil` и стараться делать интерфейсы маленькими, определяя их **по месту использования** (на стороне потребителя), а не на стороне производителя.
