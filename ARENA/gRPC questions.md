Погнали, коротко и по делу:

**HTTP/2 vs HTTP/1.1**
HTTP/2 даёт мультиплексирование запросов в одном TCP-соединении (не нужно открывать новое на каждый запрос), бинарный фрейминг вместо текста (быстрее парсится), заголовки сжимаются (HPACK), плюс полноценный бидиректональный стриминг — на HTTP/1.1 стриминг такого уровня не сделать.

**Field numbers в proto**
Номер поля — это то, как поле кодируется в бинарном виде (не имя). Если поменять номер на уже задеплоенном сервисе — старые и новые клиенты начнут читать не те данные (десериализация "поедет"), это breaking change. Менять нельзя, можно только добавлять новые номера и помечать старые как `reserved`.

**4 типа RPC**
- Unary — обычный запрос-ответ.
- Server streaming — один запрос, поток ответов (например, отдача большого списка по частям).
- Client streaming — поток запросов от клиента, один ответ (загрузка файла чанками).
- Bidi streaming — оба потока независимы (чат, live-обновления).

**Кодогенерация**
`protoc` — компилятор proto-файлов. `protoc-gen-go` генерирует Go-структуры сообщений. `protoc-gen-go-grpc` генерирует интерфейсы сервисов (клиент/сервер). Запускаются как плагины к protoc через `--go_out` и `--go-grpc_out`.

**buf**
Обёртка над protoc с нормальным управлением зависимостями, линтингом proto-файлов и breaking-change detection (buf breaking сравнивает с предыдущей версией схемы и ругается, если сломали контракт). В реальных проектах почти всегда используют его, а не голый protoc.

**Версионирование .proto между сервисами**
Обычно отдельный репозиторий с proto-схемами (или buf registry / buf schema registry), из которого все сервисы генерят код. Так все стороны видят одну и ту же версию контракта.

**Ошибки**
Возвращать не голый `error`, а `status.Error(codes.NotFound, "user not found")` или `status.Newf(...)`. Клиент через `status.FromError(err)` достаёт код и может принять решение (ретраить или нет).

**Retriable vs не retriable**
`Unavailable`, `DeadlineExceeded` — можно ретраить (временная проблема). `InvalidArgument`, `NotFound`, `PermissionDenied` — ретраить бессмысленно, это ошибка запроса, а не сети.

**Interceptors**
Unary/stream interceptor — это middleware для RPC. Используются для логирования, auth (проверка токена из metadata), recovery от паники (чтобы один упавший хендлер не ронял весь сервер), сбора метрик/трейсинга.

**Context между interceptor'ами**
Через `metadata.NewIncomingContext` / `FromIncomingContext` кладут/читают данные (токены, trace id) в context, который прокидывается по цепочке interceptor → handler.

**Deadlines**
Клиент задаёт дедлайн через `context.WithTimeout`, он передаётся на сервер в metadata. Если дедлайн истёк, сервер получает отменённый context — но сам по себе gRPC не остановит выполнение автоматически, это должен делать сам хендлер, проверяя `ctx.Err()` или `ctx.Done()`.

**Прокидывание context дальше**
Context нужно передавать дальше в вызовы БД, HTTP-клиентов, другие gRPC-сервисы — иначе дедлайн/отмена не будет работать сквозь всю цепочку вызовов.

**Балансировка / L4 vs keep-alive**
HTTP/2-коннекшен долгоживущий, поэтому обычный L4 (TCP) балансировщик размажет весь трафик по одному соединению на один под — остальные поды будут простаивать. Решения: client-side балансировка (grpc resolver + LB policy, например round_robin через DNS), headless service в k8s (клиент сам резолвит все поды), либо proxy типа Envoy/Linkerd, который балансирует на уровне L7 (по запросам, а не по соединениям).

**Health checking**
grpc health checking protocol — стандартный сервис `grpc.health.v1.Health` с методом `Check`. В k8s readiness/liveness probes дергают его через `grpc-health-probe` вместо HTTP-эндпоинта.

**Reflection**
`reflection.Register(server)` включает возможность клиенту (например grpcurl) узнать список сервисов и методов без .proto файла на руках — удобно для отладки и ad-hoc запросов в проде.

**Тестирование (bufconn)**
`bufconn` — in-memory listener, позволяет поднять gRPC сервер и клиент внутри теста без реального сокета/сети. Быстрые интеграционные тесты без риска конфликта портов.

**Graceful shutdown**
`GracefulStop()` перестаёт принимать новые соединения/запросы, но дожидается завершения уже начатых RPC, и только потом останавливает сервер. В отличие от `Stop()`, который рубит всё немедленно.
