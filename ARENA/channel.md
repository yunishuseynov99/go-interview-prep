

# Мой ответ на собеседовании: «Расскажи про channel»

---

**Channel** — это встроенный тип данных в Go, предназначенный для **коммуникации и синхронизации** между горутинами. Это реализация принципа CSP (Communicating Sequential Processes): *«Не общайтесь через разделяемую память — разделяйте память через общение»*.

---

**По внутреннему устройству** — channel это указатель на структуру `runtime.hchan`:

```go
// runtime/chan.go (упрощённо)
type hchan struct {
    qcount   uint           // количество элементов в буфере
    dataqsiz uint           // размер буфера (cap)
    buf      unsafe.Pointer // кольцевой буфер (ring buffer)
    elemsize uint16
    closed   uint32
    sendx    uint           // индекс записи в буфере
    recvx    uint           // индекс чтения из буфера
    recvq    waitq          // очередь ожидающих читателей
    sendq    waitq          // очередь ожидающих писателей
    lock     mutex          // мьютекс (не sync.Mutex, а runtime mutex)
}
```

Внутри — **кольцевой буфер** фиксированного размера и **две очереди ожидания** (суда-очереди горутин). Вся работа защищена мьютексом — channel потокобезопасен из коробки.

---

## Небуферизированный канал

```go
ch := make(chan int)  // cap == 0, буфера нет
```

**Главное свойство** — это **точка синхронизации**. Отправка и получение происходят **одновременно**:

```
Горутина A                    Горутина B
    │                              │
    ├── ch <- 42                   │
    │   (блокируется)              │
    │         ┌────────────────────┤
    │         │    v := <-ch       │
    │◄────────┘                    │
    │   (разблокирована)           ├── получила 42
    ▼                              ▼
```

- **Отправитель блокируется**, пока получатель не заберёт значение
- **Получатель блокируется**, пока отправитель не положит значение
- Данные передаются **напрямую** из стека в стек — без копирования в буфер (оптимизация runtime)

**Когда использовать:** когда нужна **гарантия**, что другая горутина получила данные. Сигнализация, handshake, точки синхронизации.

---

## Буферизированный канал

```go
ch := make(chan int, 5)  // cap == 5, кольцевой буфер на 5 элементов
```

**Главное свойство** — отправка блокируется только когда **буфер полон**, получение — когда **буфер пуст**:

```
    cap = 3

    ch <- 1   ✅ не блокируется  [1 _ _]
    ch <- 2   ✅ не блокируется  [1 2 _]
    ch <- 3   ✅ не блокируется  [1 2 3]
    ch <- 4   ❌ блокируется     [1 2 3]  — буфер полон
    
    <-ch      → 1                [2 3 _]  — писатель разблокирован
```

**Когда использовать:** когда отправитель и получатель работают с **разной скоростью** — буфер сглаживает пики. Worker pool, rate limiting, batch processing.

## Ключевые моменты, общие для обоих типов:

**Первое** — нулевое значение канала — `nil`. Операции с `nil` каналом **блокируются навсегда**. Это не баг, а фича — используется в `select` для динамического отключения веток:
```go
var ch chan int
ch <- 1   // блокируется навсегда
<-ch      // блокируется навсегда
```

**Второе** — **закрытие канала** (`close(ch)`):
```go
close(ch)

ch <- 1    // ❌ panic: send on closed channel
v := <-ch  // ✅ возвращает zero value (немедленно, без блокировки)
v, ok := <-ch  // ok == false — канал закрыт и пуст
```
Закрывать должен **только отправитель**. Закрытие — это **broadcast-сигнал** всем читателям. Именно поэтому `close` используется для сигнализации завершения.

**Третье** — **range по каналу** — идиоматичный способ читать до закрытия:
```go
for v := range ch {
    // читает пока канал не закроют И буфер не опустеет
}
```

**Четвёртое** — **направленные каналы** — ограничение на уровне типа:
```go
func producer(ch chan<- int) { ch <- 42 }   // только запись
func consumer(ch <-chan int) { v := <-ch }  // только чтение
```
Двунаправленный канал **неявно** приводится к однонаправленному. Обратно — нельзя.

**Пятое** — **select** — мультиплексирование каналов:
```go
select {
case v := <-ch1:
    // ch1 готов
case ch2 <- 42:
    // записали в ch2
case <-time.After(5 * time.Second):
    // таймаут
default:
    // ни один канал не готов (non-blocking)
}
```
Если несколько case готовы — выбирается **случайный** (чтобы не было starvation).

**Шестое** — **deadlock**. Если все горутины заблокированы на каналах — runtime детектит и выбрасывает `fatal error: all goroutines are asleep - deadlock!`.

## Сравнение в таблице

| | Небуферизированный | Буферизированный |
|---|---|---|
| `make` | `make(chan T)` | `make(chan T, N)` |
| `cap` | 0 | N |
| Отправка блокирует | **Всегда** (пока не заберут) | Только когда **буфер полон** |
| Получение блокирует | **Всегда** (пока не отправят) | Только когда **буфер пуст** |
| Семантика | Синхронизация / handshake | Очередь задач / сглаживание |
| Гарантия доставки | Отправитель **знает**, что получатель забрал | Отправитель знает только, что **положил в буфер** |

## Типичные паттерны

```go
// 1. Done-канал (сигнал завершения)
done := make(chan struct{})  // struct{} — zero bytes
go func() {
    defer close(done)
    // работа...
}()
<-done  // ждём завершения

// 2. Семафор (ограничение параллелизма)
sem := make(chan struct{}, 10)  // макс 10 одновременных
sem <- struct{}{}  // acquire
<-sem              // release

// 3. Fan-out / Fan-in
// Несколько горутин читают из одного канала (fan-out)
// Несколько горутин пишут в один канал (fan-in)

// 4. Pipeline
// ch1 → stage1 → ch2 → stage2 → ch3
```
