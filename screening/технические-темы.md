# Технические темы вакансии — шпаргалка понятным языком

---

## 1. OAuth2 / OIDC

**Разница между ними:** OAuth2 — протокол авторизации ("дать приложению доступ
к моим данным/API без пароля"). OIDC — надстройка поверх OAuth2, которая
добавляет слой аутентификации ("кто этот пользователь") через ID Token (JWT).
OAuth2 отвечает на "что можно делать", OIDC — "кто это".

**Authorization Code + PKCE:**
Классический флоу: пользователь логинится на стороне IdP (Keycloak) →
IdP редиректит обратно с коротким `code` → бэкенд обменивает `code` на
`access_token` + `refresh_token` через серверный запрос (с client_secret).
PKCE — это защита для публичных клиентов (SPA, мобилки), у которых нет
безопасного места хранить client_secret. Клиент перед стартом флоу генерирует
случайный `code_verifier`, хэширует его в `code_challenge` (SHA256) и шлёт
challenge при старте. При обмене code→token шлёт исходный verifier. Сервер
сверяет хэш. Это защищает от перехвата `code` третьей стороной (authorization
code interception) — даже если атакующий украдёт `code` из редиректа, у него
нет verifier, чтобы обменять его на токен.

**Refresh token rotation:**
Каждый раз, когда refresh_token используется для получения нового access_token,
старый refresh_token инвалидируется и выдаётся новый. Если кто-то украл
refresh_token и уже использовал его — легитимный клиент при следующей попытке
получит ошибку (токен уже "сожжён"), что сигнализирует о компрометации
(reuse detection) и можно отозвать всю сессию/семью токенов.

**Token exchange:**
Механизм, когда один токен обменивается на другой — например, сервис A
получил токен пользователя, но ему нужно сходить в сервис B с более узким
scope/aud (audience). Токен exchange позволяет обменять широкий токен на
более узкий/другой-аудиторный, не заставляя пользователя логиниться заново.
Используется для service-to-service delegation.

**Direct Grant (Resource Owner Password Credentials) и его риски:**
Флоу, где клиентское приложение само принимает логин/пароль пользователя и
шлёт их напрямую в token endpoint (минуя браузер-редирект на IdP). Риски:
клиент видит сырой пароль (нарушает принцип "пароль видит только IdP"),
невозможно использовать MFA/WebAuthn (нет интерактивной формы IdP), не
работает SSO, высокий риск фишинга через поддельные клиенты. Используется
только для legacy/trusted first-party клиентов (и то нежелательно), сейчас
считается anti-pattern, OAuth2.1 его убирает совсем.

**JWT: signing, claims, resource-side validation:**
JWT = header.payload.signature, три part в Base64. Подпись — обычно RS256
(асимметрично, приватный ключ у IdP, публичный — у ресурс-серверов для
проверки) или HS256 (симметрично, общий секрет — хуже, т.к. секрет нужно
шарить). Claims — поля в payload: `sub` (user id), `aud` (для кого токен),
`iss` (кто выдал), `exp`/`iat` (срок действия), кастомные claims (роли,
scope). На стороне ресурс-сервера валидация: проверить подпись по
публичному ключу IdP (через JWKS endpoint), проверить `exp` не истёк,
проверить `aud` совпадает с ожидаемым сервисом (защита от token
confusion — токен, выданный для сервиса A, не должен приниматься сервисом
B), проверить `iss` — что токен от доверенного IdP.

## 2. Keycloak

**Realm:** изолированное пространство пользователей/клиентов/ролей —
аналог "тенанта". Разные продукты/окружения обычно = разные realms,
они не видят друг друга.

**Client:** регистрация приложения внутри realm — у клиента свой
client_id, тип (confidential — с secret, для бэкендов; public — для
SPA/мобилок, работает через PKCE), redirect URIs, разрешённые флоу.

**Authentication flow:** конфигурируемая цепочка шагов при логине —
можно добавлять/переставлять "exec steps" (пароль → OTP → условный шаг
если устройство новое). Keycloak даёт визуальный конструктор этих цепочек.

**Required actions:** действия, которые система принудительно требует
от пользователя при следующем логине — например, "обнови пароль",
"настрой OTP", "подтверди email". Привязываются к пользователю и
выполняются один раз.

**Identity brokering:** Keycloak выступает посредником — пользователь
логинится через внешний IdP (Google, Apple, другой OIDC-провайдер),
Keycloak принимает ответ от внешнего IdP и мапит его в своего
внутреннего пользователя (account linking). Полезно, когда нужен
единый внутренний auth-слой поверх нескольких внешних источников
идентичности.

**Мажорные апгрейды:** обычно боль в двух местах — (1) миграции схемы БД
Keycloak между версиями (нужно читать release notes, что deprecated/
удалено), и (2) breaking changes в Admin REST API / themes, если у вас
кастомизация UI логина. Стратегия: апгрейд через staging-окружение,
прогон на копии прод-данных, поэтапно по мажорным версиям (нельзя
прыгнуть через несколько мажоров сразу — обычно нужно идти по порядку).

## 3. MFA

**TOTP (Time-based One-Time Password):** RFC 6238. Общий секрет между
сервером и приложением (Google Authenticator и т.п.), оба независимо
считают `HMAC(secret, current_time_step)` и получают один и тот же
6-значный код. Не требует сети на стороне пользователя при проверке.
Шаг времени обычно 30 сек, сервер допускает небольшой дрейф (±1 шаг).

**SMS/email OTP:** код шлётся через внешний канал. Минус — SMS
перехватываем (SIM swap, SS7-атаки), email — если почта скомпрометирована,
это уже не второй фактор. Слабее TOTP/push с точки зрения security, но
проще в UX и не требует приложения.

**Push-аутентификация:** на устройство пользователя (с установленным
приложением) приходит push "подтвердить вход", пользователь нажимает
Approve/Deny. Риск — "MFA fatigue"/push-bombing атаки (атакующий спамит
push, пока пользователь случайно не нажмёт Approve), смягчается
number-matching (нужно ввести число с экрана логина в push).

**Passkeys / WebAuthn:** основаны на асимметричной криптографии.
При регистрации устройство генерирует пару ключей, приватный остаётся
на устройстве (в Secure Enclave/TPM), публичный уходит на сервер.
При логине сервер шлёт challenge, устройство подписывает его приватным
ключом (обычно через биометрию/PIN локально), сервер проверяет подпись
публичным ключом. Phishing-resistant по конструкции — подпись привязана
к origin (домену), поддельный сайт не сможет получить валидную подпись.

**Origin / RP ID:**
RP ID (Relying Party ID) — домен, к которому привязан passkey (обычно
eTLD+1, например `example.com`). Origin — конкретный URL, с которого
идёт запрос. Браузер/аутентификатор проверяет, что origin соответствует
RP ID, иначе подпись не создастся — это и есть защита от фишинга
(фейковый домен не пройдёт проверку). На мобилках нюанс — нужно
настраивать associated domains (iOS) / digital asset links (Android),
чтобы нативное приложение могло использовать passkeys, привязанные
к веб-домену.

## 4. Step-up authentication, LOA / ACR

**Step-up auth:** когда базового уровня аутентификации достаточно для
большинства действий, но для чувствительной операции (смена пароля,
крупный перевод, смена email) система требует повторного/дополнительного
подтверждения (например, повторный ввод MFA), не разлогинивая пользователя
полностью.

**LOA (Level of Assurance):** уровень доверия к тому, что пользователь —
тот, за кого себя выдаёт. Чем выше операция по риску, тем выше требуемый
LOA (например LOA1 — просто пароль, LOA3 — пароль+MFA+недавнее
подтверждение).

**ACR (Authentication Context Class Reference):** claim в OIDC ID Token,
который говорит ресурс-серверу, каким именно методом/уровнем была
пройдена аутентификация в этой сессии (например `acr: mfa` vs `acr: pwd`).
Ресурс-сервер смотрит на ACR и решает — достаточно ли этого уровня для
запрошенного действия, или нужно отправить пользователя на step-up.

## 5. Сессии: ревокация, device management, hijacking protection, secure cookies

**Ревокация сессии:** возможность немедленно "убить" активную сессию
(например, при логауте со всех устройств, смене пароля, подозрении на
компрометацию) — обычно через серверный session store (Redis), а не
просто полагаясь на `exp` у JWT (JWT сам по себе нельзя отозвать
до истечения, если нет центральной проверки — поэтому часто держат
короткий access_token + отзываемый refresh_token/session id).

**Device management:** список активных сессий/устройств у пользователя
("вы залогинены тут и тут"), с возможностью завершить конкретную сессию.
Обычно хранят fingerprint устройства (user-agent, IP, иногда более
продвинутый device fingerprinting) вместе с session id.

**Session hijacking protection:** привязка сессии к доп. сигналам
(IP-диапазон, user-agent) так, чтобы резкая смена контекста триггерила
ре-аутентификацию; короткий TTL у access-токена снижает окно атаки;
ротация session id после логина (session fixation protection) — нельзя
переиспользовать pre-login session id после успешного логина.

**Secure cookies:** `HttpOnly` (JS не может прочитать cookie — защита
от XSS-кражи токена), `Secure` (только по HTTPS), `SameSite=Strict/Lax`
(защита от CSRF — cookie не улетает с кросс-сайтовых запросов), срок
жизни и домен/path ограничены минимально необходимым.

## 6. PostgreSQL: индексы, JSONB, zero-downtime миграции, performance at scale

**Индексы:** B-tree — дефолт, для равенства/диапазонов/сортировки. GIN —
для JSONB и полнотекстового поиска (индексирует "внутренности"
составных значений). Partial index — индекс только по подмножеству
строк (`WHERE status = 'active'`) — меньше и быстрее, если запросы
всегда фильтруют по этому условию. Composite index — порядок колонок
важен (left-prefix rule — индекс `(a,b)` используется для запросов по
`a` и по `a+b`, но не по одному `b`).

**JSONB:** бинарный JSON, хранится уже распарсенным (быстрее читать,
чуть дороже писать, чем обычный `json`). Поддерживает индексацию через
GIN (`@>`, `?`, `?&` операторы). Хорош для semi-structured данных
(атрибуты, которые часто меняются), но не для данных, по которым
постоянно джойнят/агрегируют — там лучше нормальные колонки.

**Zero-downtime миграции:** главное правило — разделять schema change
и deploy, не ломать обратную совместимость в один момент.
Паттерн добавления NOT NULL колонки: (1) добавить колонку nullable,
(2) задеплоить код, который пишет в неё, (3) бэкфилл старых строк
батчами (не одной транзакцией — заблокирует таблицу), (4) добавить
`NOT NULL` через `CHECK CONSTRAINT ... NOT VALID` + `VALIDATE` отдельно
(не блокирует запись во время валидации), либо в новых PG — `SET NOT NULL`
стало дешевле если есть valid check constraint. Для переименования
колонки — expand/contract: сначала добавить новую, писать в обе,
переключить чтение, потом удалить старую. `CREATE INDEX CONCURRENTLY`
вместо обычного `CREATE INDEX`, чтобы не блокировать таблицу на запись.

**Performance at scale:** `EXPLAIN ANALYZE` для проверки реального плана
(не Seq Scan там, где ждёшь Index Scan), следить за connection pool
(PgBouncer) т.к. у Postgres дорогие соединения, партиционирование для
очень больших таблиц (по времени обычно), VACUUM/autovacuum tuning
чтобы не раздувалась bloat на высоко-изменяемых таблицах.

## 7. Event-driven: outbox, idempotency, retries, DLQ

**Transactional outbox:** проблема — нужно и записать в БД, и отправить
событие в Kafka атомарно, но это две разные системы, нет общей
транзакции. Решение: в той же БД-транзакции, где меняешь бизнес-данные,
пишешь строку в таблицу `outbox` (событие как есть). Отдельный процесс
(poller или CDC/Debezium) читает outbox и публикует в брокер, помечая
отправленные. Так событие либо есть и закоммичено вместе с данными,
либо данные не закоммитились и события не будет — консистентность
без distributed transaction.

**Idempotency:** так как брокеры дают at-least-once доставку, consumer
должен уметь обработать одно и то же событие дважды без побочного
эффекта дважды. Паттерн — idempotency key (id события/запроса) +
таблица "обработанные id" или UNIQUE constraint на бизнес-операцию,
проверка "уже обработано?" перед применением эффекта.

**Retries:** при временном сбое (сеть, временная недоступность
downstream) — повтор с exponential backoff (+ jitter, чтобы не
скоррелировать ретраи многих consumer'ов в один момент). Не ретраить
бесконечно — ограничить число попыток.

**DLQ (Dead Letter Queue):** когда сообщение не удаётся обработать
после N попыток (или ошибка явно не ретраибельна — например, невалидная
схема), его перекладывают в отдельную очередь DLQ вместо того, чтобы
блокировать обработку остальных сообщений (head-of-line blocking) или
теряTь его молча. DLQ потом разбирают вручную/алертят на неё.

## 8. Hexagonal architecture + testcontainers

**Hexagonal architecture (ports & adapters):** бизнес-логика (domain/
core) не знает ничего о конкретных технологиях — она общается через
интерфейсы (`ports`), а конкретные реализации (Postgres repo, Kafka
publisher, HTTP handler) — это `adapters`, которые эти порты
реализуют/используют. Цель — domain-код тестируется без БД/брокера
(просто моки портов), а технологию (например Postgres → другую БД)
можно сменить, не трогая бизнес-логику. Отличие от просто
"layered architecture" — зависимости всегда направлены внутрь, к
домену, а не domain → infra.

**Testcontainers:** библиотека, которая поднимает реальные зависимости
(Postgres, Kafka, Redis) в Docker-контейнерах прямо во время запуска
интеграционных тестов, а не моками. Плюс — тестируешь реальное
поведение БД (реальные constraints, реальный SQL-диалект, реальные
race conditions), а не то, что "так ведёт себя мок". Контейнер
поднимается перед тестом и убивается после — тесты изолированы и
воспроизводимы на любой машине/CI без внешней инфраструктуры.
