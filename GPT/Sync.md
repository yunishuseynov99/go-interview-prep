# Package `sync`
## 1. Зачем вообще существует `sync` в Go

Go изначально проектировался как язык для **масштабной конкуррентности**.
Горутины — дешёвые, их можно запускать тысячами. Но как только:

* две горутины **одновременно читают и пишут** одну переменную
* или одна пишет, пока другая читает

ты попадаешь в **data race**.

Важно понять:

> **Data race — это не “иногда неправильный результат”, а *неопределённое поведение***.

Это значит:

* сегодня работает
* завтра падает
* послезавтра возвращает мусор

Компилятор и CPU **имеют право** переупорядочивать инструкции.

`sync` — это не “про удобство”, а про **корректность памяти**.

---

## 2. Модель памяти Go и почему без `sync` всё ломается

В Go **нет гарантии**, что:

* запись в переменную в одной горутине
* будет видна в другой горутине
* без синхронизации

Пример:

```go
var ready bool
var data int

go func() {
    data = 42
    ready = true
}()

for !ready {}
fmt.Println(data)
```

Кажется логичным, что выведется `42`.
**На самом деле — нет гарантии.**

Почему:

* CPU может закешировать `ready`
* компилятор может поменять порядок операций
* другая горутина может видеть `ready = true`, но `data = 0`

`sync` **вставляет memory barriers**, которые говорят:

> “всё, что было записано до этого момента — обязано быть видно другим горутинам”

## 3. `sync.Mutex` — базовый примитив синхронизации

### Что он делает на самом деле

`Mutex` гарантирует:

1. **Взаимное исключение** (один зашёл — остальные ждут)
2. **Правильную видимость памяти**

```go
mu.Lock()
// всё, что было записано ДО Unlock в другой горутине,
// теперь ГАРАНТИРОВАННО видно здесь
```

### Пример с реальной проблемой

```go
var balance int

func deposit(amount int) {
    balance += amount
}
```

Если вызвать `deposit` из нескольких goroutine:

* операция `balance += amount` **не атомарна**
* это:

  * чтение
  * сложение
  * запись

Две горутины могут:

* прочитать одно и то же значение
* записать его обратно
* потерять часть денег

### Правильный вариант

```go
var mu sync.Mutex
var balance int

func deposit(amount int) {
    mu.Lock()
    balance += amount
    mu.Unlock()
}
```

Теперь:

* операции выполняются строго по очереди
* состояние всегда корректно

---

## 4. Почему `Mutex` нельзя копировать

```go
type Account struct {
    mu sync.Mutex
    balance int
}
```

Если ты **скопируешь** `Account`, ты скопируешь и `Mutex`.

В итоге:

* два mutex’а
* которые “защищают” одну и ту же память
* но **не знают друг о друге**

Результат — гонка данных при полной иллюзии безопасности.

Поэтому:

* структуры с `Mutex` **передаются по указателю**
* `Mutex` всегда часть владения объектом

## 5. `sync.RWMutex` — оптимизация под чтение

### Логика

Частый кейс:

* данных читают много
* пишут редко

`Mutex` в таком случае:

* блокирует **всех**
* даже если все только читают

`RWMutex`:

* разрешает **много читателей одновременно**
* но **писатель всегда эксклюзивен**

### Как это выглядит

```go
var mu sync.RWMutex
var cache map[string]string

func read(key string) string {
    mu.RLock()
    defer mu.RUnlock()
    return cache[key]
}

func write(key, value string) {
    mu.Lock()
    defer mu.Unlock()
    cache[key] = value
}
```

### Важный момент

* если писатель ждёт → новые читатели **блокируются**
* иначе писатель мог бы ждать вечно

Это компромисс между производительностью и справедливостью.

## 6. `sync.WaitGroup` — координация, а не защита данных

`WaitGroup` **не защищает память**.
Он нужен только для **ожидания завершения горутин**.

### Что он гарантирует

* счётчик атомарен
* `Wait()` блокируется, пока счётчик не станет 0

### Классический сценарий

```go
var wg sync.WaitGroup

for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(i int) {
        defer wg.Done()
        doWork(i)
    }(i)
}

wg.Wait()
```

### Частая ошибка

```go
go func() {
    wg.Add(1) // ❌ может выполниться после Wait()
    defer wg.Done()
}()
```

`Add` **должен вызываться до старта горутины**.

## 7. `sync.Once` — гарантированная однократная инициализация

### Зачем он вообще нужен

Наивный вариант:

```go
if config == nil {
    config = loadConfig()
}
```

В конкуррентной среде:

* две горутины могут одновременно зайти
* инициализация выполнится дважды

### `Once` решает это корректно

```go
var once sync.Once
var config *Config

func getConfig() *Config {
    once.Do(func() {
        config = loadConfig()
    })
    return config
}
```

Гарантии:

* функция выполнится **ровно один раз**
* все остальные горутины ждут завершения
* память будет видна всем

## 8. `sync.Map` — специализированный инструмент

Это **не просто map + mutex внутри**.

Он оптимизирован под сценарий:

* много горутин
* ключи редко удаляются
* чтений намного больше, чем записей

Он использует:

* read-only map
* dirty map
* атомарные операции

### Когда НЕ стоит использовать

* если простая структура
* если мало конкуренции
* если нужна предсказуемая логика

В 80% случаев:

```go
map + Mutex
```

лучше и понятнее.

---

## 9. `sync.Cond` — условная синхронизация

Используется, когда:

* горутина должна **ждать условия**
* и быть разбуженной другой горутиной

Пример:

* очередь
* пул воркеров
* bounded buffer

```go
cond := sync.NewCond(&mu)

cond.Wait()    // отпускает mutex и засыпает
cond.Signal()  // будит одну
cond.Broadcast() // будит всех
```

Это низкоуровневый инструмент, чаще всего:

* либо пишут своё
* либо используют каналы

---

## 10. Почему `sync` и `channels` — не враги

Каналы:

* хороши для **потоков данных**
* управления жизненным циклом
* пайплайнов

`sync`:

* защита **состояния**
* кеши, счётчики, карты
* внутренности сервисов

Реальный Go-код **всегда использует оба**.

---

## Главное, что нужно запомнить

1. `sync` — это про **корректность памяти**, не только блокировки
2. Без синхронизации Go-код может быть **логически правильным и при этом сломанным**
3. `Mutex` защищает **инварианты**
4. `WaitGroup` — не про данные, а про **время**
5. Каналы не заменяют `sync`, а решают **другую задачу**
